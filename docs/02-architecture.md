# Architecture

AI.Server holds the whole server side: Domain (rules and invariants), Application (scenarios and interfaces to external resources), Infrastructure (HTTP, JSON, storage, secret protection, MCP tools) and Hosting (the HTTP/SSE API as `IEndpointModule`s, `AiClientServer`, the shared System.CommandLine options). Web depends only on Contracts, the Host-Web contract. Executables stay thin: AI.Host parses its command line and runs the server. Everything is composed with Pure.DI; compositions are shared as source — `Contracts/Composition.cs`, `Server/Composition.cs` and `Server/CommandLine/Composition.cs` are internal setups that consumers link and extend with `DependsOn`.

`GlobalSettings.Connections` is the unified connections catalog. A project stores a `ConnectionId`; a chat can override it. Secrets are available through `IGlobalSecretStore`. Duplicate project profiles have been removed.

Services receive interface dependencies through their constructors. Composition defines implementations and lifetimes; stateless services default to transient, while synchronization, signals and caches are shared where required. ASP.NET service-provider roots are separated from reusable server bindings. Follow the [Pure.DI conventions](30-dependency-injection.md) when adding or changing functionality.

Replaceable adapters are introduced only at the boundaries [ADR-014](decisions/ADR-014-replaceable-boundaries-and-user-scope.md) lists — user, metadata storage, binary content, model protocol, agent harness and tool execution — each with one implementation until a second is needed, and nowhere else. The ports and their one implementation today: `IUserContext` (the local user), the `I*Repository` ports pinned by contract tests (JSON documents), `IBlobStore` (`DirectoryBlobStore`), `IChatCompletionClient` (the OpenAI-compatible adapter), `IAgentHarness` reporting to an `IAgentRunSink` (`ChatAgent`), and `IToolEnvironment` (`LocalToolEnvironment`).

Everything stored and everything running belongs to a user. `IUserContext.Current` is the user of the innermost `IUserScope`, kept in the execution context by `AmbientUserContext`, and throws when no scope is active rather than falling back to anyone. Only entry points enter a scope: `UserScopeMiddleware` for every HTTP and SSE request after the origin and bridge checks (`IRequestUserResolver`; `LocalUserResolver` answers with the one local user while there is no sign-in), and the background loops for the user they work for — run recovery and chat-kind start-up and the scheduler for each user of `IUserDirectory`, a run's worker, reports and skills for the user its runtime was created for, an in-process app tool session for the user who opened it. Background work started for a user goes through `IUserScope.Run`, which enters that user explicitly instead of inheriting whoever's flow started it. User data lives under `users/<user id>/` through `IUserStorageLocation`; what belongs to the installation stays at the data root through `IInstanceStorageLocation` ([Storage](04-storage.md)). Singletons shared by all users key what they keep by path or record its user: the read caches, the run registry, reply drafts, change and navigation signals.

`ChatRunDispatcher` lives in the Application layer. Web and CLI send a single `Submit` command: Send, Queue, Fork, or Replace. The server manages the queue, idempotency, context, and result recording. `ChatSynchronization` serializes chat changes, but network requests for different branches run in parallel.

`ChatRunHostedService` recovers interrupted runs and waits for workers when the Host stops. Deletion first stops workers. SSE delivers snapshots with revisions and allows coalescing of intermediate events.

`GlobalSettingsPanel` owns settings editing; `RunStateService` stores run snapshots. The composer sends a server command. Branches have explicit stable IDs and heads.

MCP execution and the agent loop are not yet implemented: settings are available. The API and formats have been changed without backward compatibility. See ADR-006.
