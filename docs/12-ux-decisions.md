# UX decisions

Status: Accepted baseline

The goal of the interface is a compact desktop workspace, visually and behaviorally close to Codex. Earlier chosen variants are requirements for features, but do not require literally reproducing every intermediate dialog. If a decision creates unnecessary friction, priority belongs to the simple chat scenario, safety, and incremental implementation.

## Layout

- Projects and nested chats live on the left.
- The active chat branch and the composer pinned to the bottom live in the center.
- The project inspector with General, Endpoints, Security, and MCP tabs lives on the right.
- The left and right panels are resizable, collapsible, and persist their layout locally.
- On narrow screens the side panels open as overlay drawers.
- A compact dark theme is used.

## Composer

- `Enter` sends the message, or adds it to the turn in progress; `Shift+Enter` adds a line;
  `Ctrl+Enter` queues it; `Ctrl+Alt+Enter` forks the branch and runs it immediately; `Esc` stops
  the turn in progress. The keys follow Claude Code and Codex, so nobody has to relearn them.
- During IME composition the message is not sent.
- After sending the composer is cleared and keeps focus.
- Streaming and Stop are implemented as a separate stage.
- The full "branch status × action" rules (Send/Queue/Fork, auto-Resume, pre-pause, prohibition
  of Edit&Replace during generation) — see [Composer rules](15-composer-rules.md).

## Input history

- `↑` on the first line opens the history of sent messages, `↓` on the last line returns to the
  newer ones. History opens only while the field is empty: with text in it `↑` belongs to the
  caret and moves between lines, so a half-written message is never replaced. The key fires
  exactly on the edge line, not on the edge character: the entry is
  substituted with the caret at the end, and a requirement to reach position 0 would consume
  every second press on a single-line entry. Inside a multi-line entry the arrows still move
  between lines.
- The field was empty when the walk started, so that is what `↓` past the newest entry and `Esc`
  return to. While paging, the draft in localStorage is not rewritten — browsing history
  must cost nothing.
- Editing the substituted text detaches it from history: the counter goes blank, the text
  becomes a draft again, and the next `↑` starts the walk over from the newest entry.
- The `History N/M` counter sits in the status line above the field, `1/M` is the last sent
  entry. If the line is occupied by a Generating/Forking/Replacing chip, the counter becomes
  its muted prefix. The regular hint is not shown in that case.
- History belongs to the project, not the chat: formulations repeat ("run the tests", "do the
  recommended thing"), and they migrate between chats of the project. Only an accepted send
  (Send, Queue, Fork) lands there; a rejected one already stayed in the field.
  A repeat moves to the top instead of duplicating, 100 entries are stored in localStorage.
- The only key hint is `↑ for history` in the status line, when the field is empty and the
  history is non-empty. There is no history search (`Ctrl+R`) yet.

## Message queue

- The queue panel shows only what has not been sent yet. A sent command lives in the transcript,
  not in the list, every line of which would promise edit and delete.
- Nor does it show a message that is about to run: one sent to a free branch passes through the
  queue only until the worker takes it, and a "Queued · 1" flashing there announced a wait that
  never came. A message sent with Enter during a turn is listed with a "This turn" label and
  without reorder buttons, and while every row is such a message the panel says "Adding to this
  turn": it is read at the turn's next step, not when its turn comes.
- A stopped or failed run is shown as a chip at the end of the transcript, after the file-changes
  summary, together with Retry, Continue, From branch head, and Discard actions. The chip uses
  the same card as the changes summary. There is no chip for an ongoing generation: its timing
  and the Stop button already live in the composer, and a second copy added nothing.
- The `Queued · N` counter equals the number of visible rows, and `Clear` removes exactly those.
  The previous behavior depended on whether the worker was unwinding at that moment, so the
  same click produced different results. The separate "stop and clear all" action asks for
  confirmation.
- Any server rejection is shown to the user as the text the server returned. Earlier the client
  silently swallowed them, and the rejection was indistinguishable from inaction.
- Interruption preserves the already-written part of the answer as an incomplete message: both
  Stop, `Esc` and the queue's "send now" behave the same way. A retry replaces this fragment with
  the full answer.
- An error stops the entire queue: the following messages usually depend on the previous answer.

## Endpoint profiles

- The project has a default endpoint, used automatically by new chats.
- A chat stores its own EndpointProfileId; changing the endpoint affects the next requests.
- The Endpoints editor uses master-detail: list on the left, the selected profile form on the right.
- Changes are applied explicitly through Save; Cancel returns the last saved state.
- Test connection performs a short model request and does not create a message.
- The credential is stored only in the protected Host store.

## Chats and branches

- New chat creates a UI draft; the document is saved after the first message.
- The chat has Rename, Duplicate active branch, and Delete.
- Only the active branch is shown in history; alternatives are switched near the branch point.
- Edit and branch creates a new branch, keeping the original message.
- Copy copies the source Markdown.
- Clicking the chat name in the sidebar, when one of ITS branches is already open, always returns
  to the primary/original branch — this is the only explicit way to get back to it (there is no
  separate "primary branch" row in the branch tree). Bug: `SelectChatAsync` restored the "last
  visited branch" for that chat EVEN when the chat was already open — `SelectBranchTreeItemAsync`
  had just written the current (non-primary) branch as the "last" one, so the restore immediately
  returned to it, and a repeated click on the chat name stopped doing anything. The "last branch"
  restore is now skipped if this chat was already selected immediately before the click — it is
  intended for a different case (entering the chat FROM OUTSIDE: from another chat or after a page
  reload), not for repeated clicking on an already open chat.

## Icons and feedback

- A local minimal set of Lucide SVG icons is used through a JavaScript-free Blazor component.
- Icon-only buttons carry an `aria-label`, tooltip, and focus state.
- The main Save/Delete actions keep their text label.
- Common results are shown as toasts; form errors sit next to the fields.

## Agent and MCP UI

- Tool calls of one agent step are grouped into a single collapsible card.
- An Ask approval is displayed inline with Allow once, Allow for chat, and Deny.
- File changes are shown as a linked Changes card with a unified diff for view only.
- Completed turns with saved Undo snapshots offer an icon and text action in the Changes card and review header. The review's file rows use an icon-only action with a tooltip and accessible name. Undo restores the pre-turn file bytes, including pre-existing user edits, without changing the Git index. A later edit blocks that file; bulk Undo requires every remaining file to be restorable. Only a run that is generating blocks Undo project-wide, because it may still write a shared workspace file; a paused run is a standing state left by an interrupted worker, not an activity, and used to refuse Undo in every chat of the project until that unrelated queue was resumed or cleared. The historical diff and review comments remain visible after Undo. Every Undo entry point (the Changes card header, the review header, and the review's file rows) is drawn with the danger tokens rather than the accent ones, and so is the button that performs the Undo in the in-place confirmation: it discards file content the user may not have committed yet.
- These elements are implemented after the MCP connection manager and agent loop.

## Deferred

- Streaming, Stop, and incomplete responses.
- The full branch switcher and message action toolbar.
- MCP template library, approvals, and grouped tool timeline.
- FileSystem MCP changes/diff and native folder pickers.
- Search, export, and attachments.

## Implementation order

1. Workspace foundation: remove the prototype markup, inspector tabs, endpoint master-detail, default endpoint, Save/Cancel, toasts, and the minimum icons.
2. Layout and composer: resize/collapse, local layout, Enter/Shift+Enter, drafts, rename/delete.
3. Streaming.
4. Full branch UX.
5. MCP connection manager and agent loop.
6. FileSystem MCP, Changes, and diff.

## Implementation state as of 2026-08-12

The first working part of the workspace foundation has been implemented:

- the prototype markup has been removed from the DOM; the application uses a single three-panel workspace;
- the inspector is split into General, Endpoints, Security, and MCP tabs;
- Endpoints uses master-detail and explicit Save/Cancel;
- the project stores the default endpoint, and every chat stores the selected `EndpointProfileId`;
- a new chat inherits the project's default endpoint;
- the endpoint selection in the composer is saved immediately for the active chat;
- `Enter` sends the message, `Shift+Enter` adds a line, IME composition is not intercepted;
- the width of the left and right panels is changed by drag splitters and is persisted in `localStorage`;
- a local SVG icon set with `aria-label` and tooltip has been started.

Additionally implemented:

- the left and right panels collapse through icon-only buttons; the state is saved together with the layout width;
- the chat header gets buttons to restore the hidden panels;
- main successful operations and brief errors are shown through an auto-dismissing toast;
- `Test connection` performs a short real OpenAI-compatible completion through the Host gateway, uses the stored credential, and does not create messages in the chat history.

The streaming stage has been implemented:

- the Host requests OpenAI-compatible Chat Completions with `stream: true` and reads SSE `data` events up to `[DONE]`;
- credentials are resolved only on the Host and are not sent back into WASM;
- the assistant Markdown is rendered incrementally, and Send during generation is replaced with Stop;
- the user message is saved before the request; the completed assistant response is saved after `[DONE]`;
- a Stop or a stream break saves the already-received assistant response with the `Incomplete` flag;
- an empty partial assistant response is not created.

Not yet implemented in this stage: a full overlay drawer for both panels on mobile width and a specialized health-check, if a specific endpoint provides such an API.

The basic chat management stage has been implemented:

- New chat creates only a UI draft; the JSON document and the title from the first 48 characters are created on the first send;
- a chat can be renamed inline and deleted after a two-step confirmation in the header;
- Copy Markdown uses the Clipboard API and copies the source Markdown;
- Edit and branch moves the original user text into the composer and sets the branch point to its parent;
- near messages with alternative siblings a compact branch switcher appears;
- switching selects a sibling and continues its newest child path;
- Rename/Delete use revision and do not overwrite concurrent changes.

Duplicate active branch has not been implemented: it makes sense to add it together with export/import after the MCP agent loop.

## UX refinement: chat workspace

- The sidebar has only one clear Hide sidebar button; in the collapsed state only one compact icon-only Show sidebar control remains.
- In the chat header the endpoint selector sits next to the chat name and does not have a separate Configure button. Endpoint settings are available in the persistent right panel on the Endpoints tab.
- A draft chat does not show the artificial name `New chat`; the empty composer shows the disappearing placeholder `Message the assistant...`.
- Send sits in the bottom panel of the composer next to a hint about the available action; the icon and text explain the purpose.
- Project settings uses a fixed header and a danger zone pinned to the bottom, so Delete project does not change its position when switching tabs.
- Endpoints uses a profile picker and one convenient detail form, instead of two narrow simultaneously visible columns.
- The top bar of the center has been removed: the chat name is visible in the sidebar, and endpoint selection and editing are on the Endpoints tab on the right.

## Project settings placement

- The persistent right inspector panel has been removed: it took space from the chat workspace and mixed navigation with editing.
- The selected project has an icon-only `…` menu with the tooltip `Project menu` in the sidebar.
- The menu contains `Project settings`, which opens a modal tabbed window, and `Delete project` with an inline confirmation in the same menu.
- In editable tabs `Save` saves and closes the window, `Cancel` rolls back the draft and closes. The separate `X` button has been removed as a duplicate action; a click on the dimmed background is equivalent to Cancel.
- The Project settings modal size is fixed for all tabs; when the viewport height is insufficient, only the contents of the active tab scroll.
- `Save` and `Cancel` are shared across all tabs and pinned to the dialog footer; switching the tab does not change their position. Contextual actions, such as `Test connection`, stay inside the corresponding tab.
- The dialog uses an enlarged fixed size of `42rem × 52rem`, but is always constrained by the available viewport. Internal scrolling remains a fallback only for small screens or longer content.
- Adding and removing endpoints is done through compact `+` and `−` buttons next to the profile picker; the full purpose of the buttons is available through tooltip and accessibility label.
- The sidebar does not show separate product branding: the space starts right away with the navigation sections. Collapsing the entire sidebar at once is supported by **one** toggle button `.sidebar-toggle`: in the expanded state it shows `chevron-left` with the tooltip `Hide sidebar`, in the collapsed state — `chevron-right` with `Show sidebar`. This is literally "one button replaces another" from the decision above, not two separate buttons in the same position. The collapsed sidebar shrinks to `2.8rem` (`--sidebar-track`); its content and the left resizer are muted through `visibility: hidden; pointer-events: none`. Collapsing the entire panel coexists with collapsing the individual Settings/Projects sections — these are independent mechanics, like width adjustment by dragging `.workspace-resizer[data-side="left"]`.
- The `.sidebar-toggle` button is moved out of `.workspace-sidebar` and positioned absolutely relative to `.workspace-shell` (which gets `position: relative` for this), with horizontal anchoring to the track width: `left: calc(var(--sidebar-track) - 2.5rem)`. This way the same CSS declaration gives the correct place in both states (at the right edge of the expanded sidebar and at the center of the collapsed strip), and the button does not reserve vertical space above the chat area. Keeping it inside `.workspace-sidebar` is not allowed: it has `overflow-y: auto`, so an absolute child at the right edge would be clipped by the scroll container and would scroll away together with the content.
- The collapse state lives in C# (`_isSidebarCollapsed`); the `left-collapsed` class is bound on `<main>`, is persisted under a separate `localStorage` key (`ai-client.sidebar-collapsed.v1`), and is read once on `firstRender`. The layout JS module no longer manages classes — it is responsible only for width dragging; this removes two owners of one state.
- The sidebar consists of two root, independently collapsible sections — **Settings** (`Connections`/`Security`/`MCP`) and **Projects** (the list of projects and their chats). Each section is a `.sidebar-heading` with a heading button `.sidebar-heading-toggle` (chevron + label), a click on which toggles `_isSettingsSectionExpanded`/`_isProjectsSectionExpanded` and expands/hides the section content; the chevron rotates 90° through `[aria-expanded="true"] .app-icon { transform: rotate(90deg) }`. `New project` (`+`) remains a separate button next to the `Projects` heading outside the collapsible area and **automatically expands** the Projects section after creating a project — otherwise a new project would be created and selected, but invisible in the collapsed list.
- The defaults are intentionally different: **Settings is always collapsed** by default (`_isSettingsSectionExpanded` without initializer, `false`), **Projects is always expanded** by default (`_isProjectsSectionExpanded = true`) — Projects is the main working context, Settings is a secondary area. Neither is persisted (no localStorage) — every application reload returns the state to these defaults.
- In "phone" mode (`width <= 720px` — the same breakpoint already used in `@media (width <= 720px)` for the sidebar/content stack) both sections are automatically collapsed, even if the user expanded them. This is implemented through `window.matchMedia('(max-width: 720px)')` in `workspaceLayout.js:watchPhoneMode`, which checks `query.matches` immediately on attach (a page loaded in a narrow viewport immediately receives collapsed sections) and listens for `change` for live resizing; in both cases it calls `[JSInvokable] Home.OnEnterPhoneMode()` through `DotNetObjectReference`, which resets both flags to `false` and calls `StateHasChanged()`. The transition back to desktop width does not automatically expand the sections — the user returns to the regular defaults only on the next full reload.
- In phone mode the sidebar is always expanded, and the `.sidebar-toggle` button is hidden (`display: none` inside `@media (width <= 720px)`): in the vertical layout the panel already occupies the full width above the chat, so there is no point in collapsing it to a `2.8rem` strip. `OnEnterPhoneMode()` additionally resets `_isSidebarCollapsed` to `false` — the state is brought into correspondence with reality, not just overridden by styles, otherwise a flag saved from desktop would leave the sidebar contents hidden (`visibility: hidden` from `.left-collapsed`) while the expand button is unavailable. For the same reason, `LoadSidebarCollapsedAsync()` is called BEFORE `WatchPhoneModeAsync()`: otherwise loading a saved `true` would happen after the reset and would collapse the panel again on phone.
- The tradeoff is consciously accepted: on the first application load (outside phone mode) the active project and its chats are selected automatically (as before) and immediately visible thanks to the default-expanded Projects; in phone mode the same selection happens, but the list is visually hidden until the user expands the section manually — collapsing affects only the visibility of the list in the sidebar, not the internal state selection.
- When the navigation is not visible (the Projects section is collapsed **or** the whole sidebar is collapsed) and a project is selected, a compact `.conversation-context-header` of the form `Project › Branch` is shown above the chat feed with a chevron separator — otherwise the user cannot see at all what is currently open. The condition is deliberately "OR" over two independent collapsing mechanisms: a collapsed sidebar hides the expanded Projects section too. When the navigation is visible the header is not needed and is not shown — the sidebar already shows the selection through `.selected`.
- The second element of the header is the **active branch**, not the chat. The main ("root") branch has no name of its own: `GetBranchTreeItems()` returns only the branches from forks, and the chat itself plays the role of the main branch — that is why `GetContextBranchTitle()` substitutes the chat name there. So the header always consists of exactly two elements and on any branch shows the same name that is highlighted in the sidebar tree. The active branch is determined through `GetSelectedBranchItem()` — the deepest branch containing the current `_branchLeafId`; earlier that logic lived inside `GetSelectedBranchId()`, now `GetSelectedBranchId()` is expressed through it, so that the branch selection order is not duplicated in two places.
- The composer textarea grows in height automatically as the user types (after the behaviour in Codex): the JS `chatComposer.js:attach` listens to `input`, sets `height:auto`, then `height:scrollHeight+px`; the CSS `max-height:40vh` plus `overflow-y:auto` limit the growth and enable an inner scroll when the content does not fit. `resize:none` — the user cannot drag the corner by hand (that would conflict with the auto height). Returning to `min-height:4.5rem` after a programmatic clear/substitution of `_chat.Message` (sending a message, "Edit and branch", deleting the active chat) goes through the `_composerNeedsResize` flag checked in `OnAfterRenderAsync` (the same pattern already used for `_scrollMessagesToBottom`): the JS `resize()` must read the `scrollHeight` of the value already RENDERED by Blazor rather than measure the height right inside the C# handler — a call immediately after assigning `_chat.Message` could measure the old content, not yet updated in the DOM, since JS interop may run before Blazor finishes the render.
- To the left of the chat text a history marker strip (`.history-markers`) is shown — navigation WITHIN one branch; navigation between chats and branches stays in the sidebar. The strip sits in the left gutter of the centred message column and is positioned absolutely inside `.messages-area`, so it does not shift the text. Its width was chosen to fit even the minimal gutter `2rem`: at a viewport of 820px the strip ends at 270px and the text starts at 276px.
- The markers are laid out evenly — one slot per message (not proportionally to the scroll height). The current position is shown as a fisheye through `scaleX`, but differently in two modes: while the user is not hovering, the peak is determined by scrolling (discretely, by the index of the neighbouring messages, range 0.4–1.0). On hover the cursor itself bends the strip — the peak follows the cursor continuously by pixel distance (radius ~70px, quadratic falloff), and the amplitude is roughly twice as large (0.15–1.45), because a mouse gesture is an explicit "look here" rather than a background state. At the hovered peak a tooltip with a preview of the message text (`.history-marker-tip`) also appears, positioned on that same message.
  - Current shape (supersedes the numbers in this and the following entries about the fisheye amplitude, centred origin and endpoint floor): scroll and hover share one bend, `applyBend` in `historyMarkers.js` — linear falloff over 64px (about four marker slots on either side), scale 0.55 at rest up to 2.0 at the peak, no separate floor for the first and last markers. `transform-origin` is `left`: every dash starts on one line and the bend grows only towards the message column; every marker targets a right-aligned user question, so that side of the gutter is empty. Resting dashes are a dim `--color-text-faint` (45% over transparent) and brighten to the full faint tone along the bend through `--history-marker-focus`, a 0..1 number written next to the transform; the active marker is `--color-text-strong`. The strip is no longer dimmed as a whole while the pointer is away, so the peak reads at rest too.
  - `transform-origin` of a marker is `center`, not `left`: with the hover amplitude the peak can exceed 1.0, and if the growth went only to the right, on a narrow screen (gutter `2rem`) it would run into the message text. Centring splits the growth in half — one half goes left into the empty space of the gutter — and in the measured worst case (viewport 820px, gutter 32px) leaves a margin of ~2px to the text instead of a negative one. The same measurement gave the amplitude ceiling of 1.45 rather than literally 1.6: on that narrowest screen the difference between "safe" and "creeps under the text" is a fraction of a pixel.
  - The role is encoded by brightness (the user is lighter) and the states by the colour of the existing palette (generating, unread, incomplete, error); the fork point is not a second dash but a short vertical tick to the left of the main bar (`::after`, `left:0`, `.history-marker-fork::before` shifted right through `margin-left`, so that the room for the tick is not overlapped). The tick is vertical, not diagonal: a diagonal line would visibly skew under a horizontal `scaleX`, while a vertical one is not distorted by it and only shifts along X together with the growth of the bar.
  - The strip scrolls on its own and does not show its own scrollbar (`scrollbar-width: none`); the native scrollbar of the feed stays on the right.
- The strip is hidden when the feed fits the screen entirely (class `idle`) and in phone mode, where there is no gutter. The markers are not focusable (`tabindex="-1"`, `aria-hidden` on the strip): duplicating the navigation with 200 tab stops is harmful, and accessible navigation remains in the sidebar and in the feed itself.
- The marker group is centred vertically (`justify-content: safe center`), and the gap between markers is `0.55rem`. The marker button itself is `0.7rem` high and serves as the hit area, while the visible dash is drawn by `::before` with a height of 2px — otherwise one would have to aim at a 2-pixel line. The `safe` keyword is needed so that on overflow the centring does not cut off the start of the list.
- The CSS `:hover` on the hovered marker stays separate from the JS fisheye and reacts with colour (white) and a slight thickening of the dash/tick — this does not conflict with the continuous growth from the cursor but complements it with a precise accent on the literally hovered element. The marker colour is set by the `color` property, and the dashes are drawn with `currentColor`.
- The state colours are declared with a doubled class (`.history-marker.history-marker-failed`) in order to override `.active` and `:hover`. Otherwise a failed marker that the user merely scrolled to would turn white and stop reading as an error.
- The marker scale is set by an inline `transform: scaleX()` from JS, not by `width` and not through `var()` in CSS: `transform` does not touch layout, so scrolling and hovering cause no reflow. The active position is computed from the `offsetTop` of the messages, cached before `scrollHeight` changes, so that the scroll handler does not measure every message on every frame. The edges are pinned explicitly: at the very top the first marker is active, at the very bottom the last one, otherwise the "quarter of the screen" anchor misses the outermost messages.
- `render()` in `historyMarkers.js` is called from `scroll`/`mousemove`/`mouseleave` DIRECTLY, without `requestAnimationFrame`. The first version wrapped it in rAF (the standard practice for throttling frequent events), and because of that the user reported that the fisheye did not follow the cursor at all. Diagnostics (a click on a marker worked, so `attach()` had run and the listeners were alive; a synthetic `mousemove` without the rAF wrapper — through a direct call of `refresh()` — worked too) showed that it was precisely the rAF callback that did not fire. The cause is not the code itself but the fact that `requestAnimationFrame` is not guaranteed to run in a number of ordinary situations (window not focused, power saving, background tab) — an effect that does not always work is worse than an effect that costs a little more CPU for a dozen buttons. Incidentally, the same test confirmed that recreating the `<nav>` DOM node (for example, when going into Settings and back) does not break re-attachment — `SyncHistoryMarkersAsync` in `Home.razor` correctly calls `attach()` again when the section becomes visible once more.
- The marker tooltip (`.history-marker-tip`) lives as a sibling of `.history-markers`, not inside it: initially it sat inside the feed and was positioned through `left: calc(100% + 0.5rem)` relative to it, but `.history-markers` uses `overflow: hidden auto` (needed for the strip's own scroll), and that same rule clipped a tooltip sticking out beyond the right edge of the strip on X — so it was never visible, on any hover. Fixed by moving `<div class="history-marker-tip">` out of `Home.razor` and making it a sibling of `<nav class="history-markers">` inside `.messages-area` (which has no `overflow`), and by positioning through `getBoundingClientRect()` in JS instead of `offsetTop`/the CSS `left: 100%` — both values (`top`, `left`) are now computed from `tip.offsetParent` (`.messages-area`) rather than from the strip itself, and correctly account for the inner scroll of the strip (`strip.scrollTop`) through live rectangles instead of cached offsets.
- The rendering of message markdown (`MarkdownRenderer.Render`, Markdig + `HtmlSanitizer`) is cached by `message.Id` instead of being called directly from the markup. The reason: `@bind:event="oninput"` on the composer re-renders the whole `Home` component on every character typed, and without a cache that re-parsed and re-sanitised the markdown of every message of the branch on every keystroke. Measured on a test chat of 24 messages: ~65ms per keystroke without the cache against ~30ms with it — and this grows linearly with the number of messages in the branch, so on long chats the effect was much more noticeable ("slow text input"). The streaming message (`activeRun.StreamingContent`) does not go through the cache — its content changes on every chunk anyway, so a cache is useless for it. The tooltip preview (`GetMessagePreview`) is cached in the same way — previously `ReplaceLineEndings` ran over a full copy of the message content on every render for the sake of a 36-character preview in a data attribute of the history feed.
- `GetSelectedRun()` was called from the markup of `Home.razor` about 9 times per render, and each call indirectly (through `GetSelectedBranchItem` → `GetBranchTreeItems`) rebuilt the whole branch tree of the chat — `GroupBy` plus several `ToDictionary` plus `DistinctBy` plus a depth walk for every root, over ALL messages of the chat (not only the visible branch). That turned out to be far more expensive than the message list itself: caching `GetBranchTreeItems()` by the reference of `_selectedChat` (it is always replaced as a whole and never mutated — the same invariant as with the message cache) reduced the time from ~28.5ms to ~11.5ms per keystroke on the same test chat — more than the markdown cache gave.
- The message list and the history feed were moved into a separate component `Components/MessageFeed.razor` instead of staying part of `Home.razor`. The reason: even after all the caches above, `@bind:event="oninput"` on the composer still causes `StateHasChanged` for the whole `Home`, and Blazor cannot skip the rebuilding of the render tree of ONE component partially — only the whole `BuildRenderTree` at once, or (for child components) not calling it at all. `MessageFeed` overrides `ShouldRender()`, comparing the incoming parameters (`SelectedChat` by reference, `BranchLeafId`/`ForkSourceId`/`MessageBranchMenuId` by value, `SelectedRun` by reference — all these objects are always replaced as a whole in the project and never mutated, so reference comparison is correct and cheap) with the last rendered ones — and does not rebuild the message list at all if none of them changed. The actions that change the chat state (Copy/Fork/Edit/Edit-and-replace/switching branches/keys in the branch menu) are passed out as `EventCallback` parameters and are still performed in `Home` (which also holds `_forkSourceId`/`_replaceSourceId`/`_branchLeafId`/the composer focus). The effect on the same test chat (24 messages): ~11.5ms → ~7ms per keystroke, and — more importantly — the message list is not rendered at all on keystrokes where no parameter changed, so the dependence on the number of messages in the chat practically disappears from the typing budget (previously, even with the caches, typing stayed ~0.3ms more expensive for every additional message in the branch, because Blazor still walked the `@foreach` and built a render tree for every message on every keystroke).
- The history markers (`historyMarkers.js`, the JS module `attach`/`dispose`, the `ElementReference` fields `_historyMarkers`/`_messagesContainer`) moved together with the message list into `MessageFeed.razor` as a whole — it is a self-contained subsystem with its own lifecycle, and `Home` should no longer know anything about it. `Home` only manages scrolling to the bottom of the chat — it exposes `MessageFeed` through `@ref` and calls the public `ScrollToBottomAsync()` instead of a direct JS call on `_messagesContainer`, which now belongs to the child component.
- The chat endpoint switcher (`.composer-endpoint-trigger`/`.composer-endpoint-menu` in `Home.razor`) reuses the already existing but previously unwired chain `SelectChatProfileAsync` → `ChatHistoryApi.UpdateEndpointAsync` — the backend for a per-chat endpoint was already ready, only the UI was missing. The fade is a gradient (a soft edge), not a CSS transition/animation: the state change on scroll happens instantly together with the rest of `render()`; "smooth" here refers to the shape of the edge, not to an animation of the mask appearing or disappearing.
- The first and the last marker in the feed are always at least twice as long as an ordinary marker at rest (`ScrollEndpointFloor`/`HoverEndpointFloor` = `ScrollMinScale`/`HoverMinScale` × 2) — but that is a FLOOR (through `Math.max`), not a MULTIPLIER on top of the current fisheye scale. The reason: if the doubling multiplied with an already active/hovered state, the peak scale of an outermost marker could reach ~2.9 (2 × `HoverMaxScale` 1.45) — far beyond the safe margin to the message text chosen earlier specifically for the narrowest supported gutter (see the entry about `transform-origin`/the 1.45 ceiling above). `Math.max(scale, floor)` gives exactly the same "always noticeably longer" at rest, but never raises the ceiling above the already verified safe maximum.

- The tooltip was clipped by the browser window at the top/bottom when the hovered marker was at the very edge of the feed (a marker near the top → the upper half of the multi-line tooltip, centred through `translateY(-50%)`, went above the visible area). - The hint arrows blinked unstably at the scroll boundary — `canScrollUp`/`canScrollDown` were compared with a tolerance of 1px, while `scrollHeight`/`clientHeight` can fluctuate by fractions of a pixel between calls (font metric adjustments, fractional zoom), which made the comparison "jitter" back and forth at the very boundary. The tolerance was increased to 4px (`ScrollEdgeSlackPx`, the same order as the tolerances in `scrollActiveIndex`). The arrows were also enlarged (SVG 0.75rem → 1.1rem) and made interactive: hovering an arrow continuously scrolls the strip in its direction through `setInterval` (not `requestAnimationFrame` — the same reason as with `render()`: rAF does not reliably tick in a collapsed/background window), stopping on `mouseleave`. `pointer-events` on the arrow is enabled ONLY in the visible state (`.visible`), otherwise an invisible arrow that still occupies space would intercept the cursor from the strip underneath.
- The first version of hover scrolling mistakenly scrolled `scroller` (`.workspace-messages`, the chat message feed) instead of `strip` (the `.history-markers` itself) — the same confusion crept into `updateFade()`: the fade/visibility of the arrows were computed from the scroll of the CHAT rather than from the scroll of the MARKER STRIP itself, which has its own independent `overflow: hidden auto` and its own content extent. Both places were switched to `strip.scrollTop`/`scrollHeight`/`clientHeight`. Scrolling the active marker into view (`scrollActiveIndex`/the "quarter of the screen" anchor) is still computed from `scroller` — that is about which message is currently visible in the chat and must stay tied to the chat. A side effect: while the cursor is on an arrow, the automatic return of the active marker into view (`strip.scrollTop += ...` in `render()`) is disabled through the `arrowHovering` flag — otherwise it would immediately override the manual arrow scroll on every tick of `setInterval`, since `render()` is called on every tick (the strip has no `scroll` event of its own that would trigger an update by itself).
- Hover scrolling looked like an instant jump rather than gradual movement: with a short strip (few questions) the whole scroll range is a few dozen px, and a fixed speed of 14px per tick in 16ms covered it in 1–2 ticks, so the eye simply had no time to notice the movement — the arrow also disappeared almost immediately. Replaced with acceleration: the speed grows from `HoverScrollStartPx` (2px) to `HoverScrollMaxPx` (9px) over `HoverScrollAccelTicks` (36 ticks, ~0.6s), so that even a short range is scrolled in several noticeable steps instead of one. In addition the arrow gets the class `.scrolling` (accent colour + `scale(1.15)`) for the whole duration of the hold — a visible confirmation that the gesture has been recognised and the strip really moves, separate from the simple `:hover` highlight in white.
- The fisheye amplitude was increased (`ScrollMaxScale` 1.0 → 1.25, `HoverMaxScale` 1.45 → 1.55) — previously the active marker during plain scrolling (without hovering) was exactly at its base size (peak = 1.0, i.e. merely "not squeezed" rather than genuinely convex), which barely read as a fisheye. In the course of verification it turned out that the old ceiling (1.45, "a couple of px to the text on the narrowest screen") was based on an outdated calculation: back then the markers corresponded to ANY message, including the assistant's (whose text starts right at the edge of the gutter). After filtering the feed to user questions only (see the entry above about "show only my questions") every marker points exclusively at `.workspace-message.user`, and that one is `margin-right: 0`, aligned to the RIGHT edge of the column, with plenty of empty space on the left. A measurement at the narrowest supported width (just above the phone-mode cut-off of 720px) showed a margin of hundreds of px to the actual text — growth to the right is now practically unlimited. The real ceiling is on the OTHER side: growth to the left is limited by the strip's own inset (`left: 0.5rem`) from the edge of the container; by that calculation the ceiling is closer to ~1.7, so 1.55 still leaves a margin.

First: the `MutationObserver` handler works DIRECTLY, without `requestAnimationFrame` (the same reason as with `render()` in `historyMarkers.js`: rAF does not reliably tick in an inactive window — with it the correction did not work at all). ## Chat switching: cancellable, and rendered tail first (2026-09-16)

- Measured first, on a real project of 25 chats: the server answers a chat request in 10–40 ms, deserialising its JSON costs 5–70 ms, and rendering the transcript (Markdig plus HtmlSanitizer) costs 150–550 ms on desktop JIT — several times that in the browser's interpreter, since the Web project is not AOT-compiled. The delay between clicking a chat and seeing it is therefore almost entirely client-side rendering, not the network.
- Opening a chat is cancellable and last-click-wins. Every selection carries a `CancellationTokenSource`; a newer click cancels the older one, its HTTP request is abandoned rather than deserialised, and each `await` is followed by a guard so an abandoned selection cannot write selection state. Before this, two quick clicks raced and the slower response could land last, leaving the wrong transcript open.
- The sidebar highlight follows the click, not the data. `_pendingChatId` is set synchronously, so the row is selected within ~15 ms while its transcript is still loading; a click no longer looks ignored for the length of a render.
- Marking a chat read and recording "where I was" happen after the render that shows the transcript, not before it. They are a server round-trip and a storage write, and neither changes what is on screen.
- A transcript opens at its tail: the last 10 feed items render first, the rest one frame later. Measured on a 160-message branch: first content at ~0.5 s instead of ~1.6 s. The limit is decided in `OnParametersSet`, not while rendering — it is passed to `TranscriptRenderBoundary` as a parameter, and a parameter set during the render reaches the boundary a render too late, which leaves the transcript permanently truncated.
- The scroll anchor is suspended while a remembered position is being restored. Anchoring exists to hold the transcript still when content appears above it, which is exactly what the expansion does, so left on it measures the drift the restore itself introduced and undoes it.
- `historyMarkers.js` advances its restore loop on a timer when frames stop coming. `requestAnimationFrame` does not tick in a tab that is not being painted, and the loop — which re-applies the scroll target until the height settles — would otherwise never finish, leaving both the feed and the caller's await hanging.
- Five transcripts stay warm instead of two, in both the chat-details cache (`Home`) and the rendered-markdown cache (`MessageFeed`). Returning to a recently visited chat renders from cache in ~0.1–0.4 s; the cost is memory, and five is the point where a realistic back-and-forth is covered without pinning a whole project's history in the browser.

## Chat list order: manual for pinned, activity for the rest (2026-09-28)

- Pinned chats keep the order the user gives them; nothing that happens in a chat moves one. The rest follow activity, newest first, so a chat with a new message or reply rises to the top of that zone, and a new chat appears first under the pinned ones. Dragging an unpinned chat among the unpinned ones does nothing, because the next message would undo the position anyway.
- Activity is the user's message, the end of a reply (including a partial one saved on interrupt) and a failed run. Tool calls and their results do not count: a long run otherwise kept jumping its chat to the top on every step. Renaming, pinning and comments never counted. A failure writes no message, so the Host records the moment on the chat (`ChatThread.MarkActivity`) and the document keeps it.
- The order of pinned chats is a fractional key per chat (`IPinOrderKeys`, base-62, compared ordinally): a move rewrites only the moved chat. Chats pinned before this existed have no key and come first, in the order they were pinned; they get keys the first time something is placed in front of one of them.
- Drag and drop uses pointer events, not the HTML5 API, which has no touch support and no control over the drop line (`chatListDrag.js`). The whole row is the handle; a mouse drag starts after 5 px so a click still opens the chat, and on touch a 400 ms long press starts it while an earlier move stays a scroll. A thin divider closes the pinned zone: a drop above it places the chat in front of the row under the line, pinning it if needed; a drop below it unpins. With nothing pinned, a dashed "Drop here to pin" zone appears at the top while dragging. The ghost says Pin or Unpin when the drop would change that. `Esc` cancels, the list scrolls at its edges, and holding over "Show N more" opens the next page.
- Pinning from the menu or `Alt+P` puts the chat last among the pinned ones, so the order already given stays. `Alt+↑`/`Alt+↓` move a focused pinned chat within the zone and announce the new position; there are no Move up/down menu items.
- The list re-reads its order when a run in the project starts or ends, not only after the user's own actions. While a mouse is over the list or a chat is being dragged the new order waits and is applied when the pointer leaves, so no row moves under the cursor. Rows that move slide to their new place (FLIP, 180 ms, off under reduced motion).
- A chat without messages stays out of the list until its first message, whoever created it; the open chat is the exception, because its first message may still be on the way to the Host when the list is re-read.

## Typing while a run works (2026-10-01)

- The Web client is Blazor WebAssembly without threads: .NET runs on the browser's main thread, the one that also handles keystrokes. While a run worked, that thread was busy for most of the time, so characters typed into the composer appeared late. Measured on a 70-turn chat with a 30 s tool-using turn and typing every 120 ms: before, 75 long tasks (5.9 s of blocked main thread), main-thread lag p95 62 ms and 9 stalls over 100 ms, a keystroke's own handling p95 60 ms; after, lag p95 19 ms, one stall over 100 ms, keystroke p95 21 ms.
- Every turn of the transcript has its own render boundary (`TranscriptTurnBoundary`). The feed-wide boundary had to let through every tick of the running turn — the once-a-second timer, the growing draft, tool progress — and each one rebuilt every turn above it, including each `ToolActivityGroup`, whose parameters Blazor always treats as changed. A finished turn now redraws only when its messages (compared by reference) or something it shows changes. The stamp keeps per turn what used to be feed-wide: the branch leaf moves with every message a run writes, the running turn's usage arrives as a new object with every snapshot, and the ledger and checkpoints are reloaded after every turn, so as shared values each of them redrew the whole transcript.
- The running turn's live and streaming text keep their last rendered Markdown, since the turn redraws on ticks that do not change the text.
- The draft of the model step in flight goes over the event stream as an append (`DraftAppends`) like streamed answer text. It was published as a whole snapshot about seven times a second, and a snapshot carries the file changes with their diffs and the recent messages. Diffs the previous frame already carried are left out (`KeptWorkspaceChanges`), and so are the messages this stream already sent. On the measured turn the stream went from 1.08 MB to 0.4 MB, most of it parsed on the main thread.
- Tool results go in the message tail without their body (`ContentOmitted`), as they already did in the transcript; the page loads a result when its step is opened. A chat whose one turn read a few large files was still freezing for up to 0.7 s at each read: every result came over in full, up to 850 KB of JSON, for a step that is folded away. On a copy of that chat with 600 KB reads the stream went from 7.8 MB to 0.56 MB and the longest main-thread stall from 706 ms to 27 ms.
- The run's question and final answer are in the message tail as well as its tool steps. Without them the open chat could not apply the tail and loaded the whole transcript at the start and at the end of every turn, 200–450 ms each on that chat. A `data-changed` signal no longer reloads the open transcript when the chat list shows the same revision: every save moves the revision, and the reload brought the same messages as new objects.
- `runEvents.js` hands the page every frame, oldest first, in batches. It used to keep only the newest frame while the page was busy, but every frame after the first is a change against the previous one: under load streamed text and status changes were dropped. A batch is drawn once, and not at all when it only carries text for chats that are not open.

The shell carries it as `data-widgets="open|closed|unavailable"`, and the layout script asks for changes through `Home.SetChatWidgetsOpen`. It is not a class on `<main>` any more: a re-rendered class attribute wiped the classes the script sets there (`sidebar-collapsed`, `is-resizing`).
- Phone width (`<= 900px`; it was `<= 720px`, which left windows of 720–900px with the sidebar in the grid and the widget column floating over the chat) no longer stacks the sidebar above the chat. The conversation takes the whole screen and both panels are drawers over it, folded on every entry into phone width; the header toggle buttons and the dividers are hidden there. A swipe to the right opens the sidebar, a swipe to the left opens the widget column; the opposite swipe, a tap on the shade, Escape or choosing a chat, search, archive or a settings section closes the drawer. A mouse resting for 200ms within 12px of the left or right window edge brings that drawer out over the chat for as long as the pointer stays on it; 300ms after the pointer leaves it the drawer goes back, unless one of its menus is open. A drawer opened by a swipe stays until it is dismissed. Swipes that start in something that scrolls sideways, such as a code block, are left to it. Ctrl+B toggles the sidebar drawer.
- The wide-screen collapse state and widths are not touched by the phone layout and come back when the window widens again.

## Filtering the settings lists (2026-10-06)

- Connections, MCP, Memory and Skills share one filter field (`SettingsFilterField`) above the list. It is shown for every list that has rows, so it is always in the same place; an empty list goes without it unless it still holds a query.
- Every word of the query must occur, ignoring case and order, in what the row is about: a connection's name, URL, model and "good for"; a server's name, URL, command and status; a memory entry's title and text; a skill's name, id, description, source and aliases. The words are marked in the rows that remain, in the accent tint search results use.
- An MCP server is also kept by its tools: the row then says how many tools match, and opening it goes to its Tools page filtered by the same words. The Tools page uses the same field.
- The field shows `shown/total` while it filters. Ctrl+F focuses it, Enter opens the first remaining row, Escape clears the query and only an empty field lets Escape close the drawer. Adding an item clears the filter so the new row is visible.

## Recents in the sidebar (2026-10-08)

- Under the project list, a Recents section lists the chats with the latest activity across every project, three at first; Settings → Sidebar → Recent chats sets that number from 1 to 10 for this client (`ClientSettings.RecentChatCount`). `Show more` opens it to twice that number, and to at least ten, and `Show less` folds it back; the heading itself folds the whole section away. Both choices are remembered in the browser (`ai-client.sidebar-recents.v1`).
- A row is the project's own chat row, drawn by the same code (`RenderChatNavRow`, `RenderChatBranchRows`): icon, branch count, run status, rename and the chat and branch menus. The project is not repeated in the row; its name is in the tooltip. Only dragging and the pinned-order keys stay on the project's list, since the order they change is that project's. The menu acts on the chat's own project, so a chat of another project can be pinned, renamed, archived or deleted without opening it; tool permissions and reviews open the chat first. A chat listed in both places opens its menu or rename editor only where it was asked for.
- The open chat's branches are listed in one place only. A chat opened from Recents folds its project's chat list, the way every other project's is folded, and its branch tree shows under the Recents row; the folded project shows the status dot other projects show. Clicking that project unfolds it on the open chat, and opening anything another way (a project, a new chat, search, a notification, a model's navigation or the guide) unfolds it as well, so the list is back where the user expects it.
- Activity is the same moment that orders a project's list. The Host answers `GET /api/chats/recent` (no archived chats, none without a message yet, and no scheduled chats: those belong to the Scheduled section, and filtering them out at the Host keeps them from spending one of the few Recents places before the section's own rows are counted); the open project's part of the list is taken from its live chat list, so only the other projects are re-read: on switching projects, on a data-changed signal and when a run in another project starts or ends.
- When chats shown in Recents have stopped work — paused, interrupted, failed with Resume among its recovery actions, or idle with messages queued, the unfinished-work widget's rule — the heading offers `Resume all` with their count. Only the chats on screen count: not those under `Show more`, and nothing while the section is folded. The runs resume one after another, each in its chat's own project, without opening anything; the button shows which one is in flight.
- Under Recents, a Notifications section lists the chats the notification history still remembers, whether or not their notification has been read — the bell's rule (not seen and not resolved) decides which of them show a dot, on the chat itself or on one of its branches, across projects, the newest notification first. It shows three chats at first; Settings → Sidebar → Notification chats sets that number from 1 to 10 for this client (`ClientSettings.NotifiedChatCount`), `Show more` opens the rest, it folds the same way, and its heading counts the unread notifications.
- Reading a chat does not remove its row. A chat leaves the section only once the chats that came after it have pushed it past the window the section remembers — `Show more` opens to twice the shown number and to at least ten, exactly as Recents does; a chat that has been read orders by the last notification it had, so it keeps the place it held, and chats with something unread sort ahead of it. Otherwise the row disappeared the very moment the user clicked it, which read as the section silently losing a chat rather than as the notification having been dealt with. Resolving an action notification keeps its entry in the history, so that chat keeps its row too; the section lists what the history still holds and is bounded by the window alone, not by the read state. The chat opened from here is never the one pushed out, so its row cannot vanish from under the pointer.
- The branches the notifications are about stand under their chat even while it is closed, so a fork that finished or failed is one click away; their names come from the open chat, the client's cache or, for a chat that is neither, its transcript read once from the Host. A dot at the end of a row says the notification is waiting: what needs an action, then a failure, then news. Opening the chat row (when the main line has the notification) or a branch row opens that branch at the notification's message, like the bell, and reads the branch's notifications.
- A chat opened from Notifications folds its project as Recents does and shows its whole branch tree there; it stays listed while it is open even once nothing in it is unread, so the row does not vanish from under the pointer.
- Opening a chat from another project makes it the project's remembered chat first, so project and chat open in one step instead of passing through the project's empty composer.

## Scheduled in the sidebar (2026-10-08)

- Under Notifications, a Scheduled section lists the scheduled chats the Host will act on within the next day, across every project, the soonest first, and under them the chats whose schedule has finished its work, the run that ended last first; the soonest of a run the Host was asked for now, a retry and the next occurrence decides where a pending chat stands. The section is absent while there is nothing to show, so an ordinary sidebar keeps its shape.
- A run that finishes does not take its chat out of the section the instant it ends. Such a chat keeps a plain row — no countdown, since there is nothing left to run — and is pushed down by the newer ones until it falls past the window the section remembers, exactly as Notifications treats a notification that has been read; what is still coming always leads, so a chat that has merely finished can never push a run that is about to start out of the window. A run still going, or waiting for a person, has not finished: the dispatcher still has work for it and it keeps a countdown of its own. A chat whose next occurrence is further away than the window counts as finished too, or a weekly schedule would lose its row after every run simply because nothing comes due again today. The guide's schedule demo is never listed at all.
- A row is the project's own chat row, drawn by the same code (`RenderChatNavRow`), leading with how long is left: `now`, `~33s`, `~5m`, `~3h`, `~2d`; a chat whose schedule has finished its work shows without one. Its project is not repeated; the tooltip names it as everywhere else. Opening the row opens the chat as Recents does: the project folds into this section, the open chat's branch tree is shown under it, and the row stays listed while the chat is open. Escape on a chat row hides only that chat (`data-soon-chat-id`); Escape on the heading folds the whole section and gives the keyboard back to the open project.
- The section folds and pages like Recents and remembers both choices in the same browser entry (`ai-client.sidebar-recents.v1`): three chats at first, `Show more` opening to twice that number and to at least ten; a chat finished long enough ago is forgotten once newer entries push it past that window. Settings → Sidebar → Scheduled chats sets that number from 1 to 10 for this client (`ClientSettings.SoonChatCount`).
- The row is drawn a second time in its finished form: the open chat is added on top of the window rather than inside it, so a row cannot vanish from under the pointer once newer chats have pushed its chat out — the same guard Notifications uses.
- The Host answers `GET /api/scheduled-chats/soon` (`limit`, `horizonMinutes`; the window defaulting to a day and capped at a week), reusing the dispatcher's own due rule (`ScheduledChats.DueAt`) so the sidebar and the scheduler never disagree about what comes next, and listing the chats whose schedule has finished its work under the pending ones; a demo chat is never listed.
- The three sections under the project list read top to bottom exactly as Settings → Sidebar does: Recents, Notifications, Scheduled.
