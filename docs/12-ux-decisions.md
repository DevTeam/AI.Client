# UX decisions

Status: Accepted baseline

The goal of the interface is a compact desktop workspace, visually and behaviorally close to Codex. Earlier chosen variants are requirements for features, but do not require literally reproducing every intermediate dialog. If a decision creates unnecessary friction, priority belongs to the simple chat scenario, safety, and incremental implementation.

## Layout

- Projects and nested chats live on the left.
- The active chat branch and the composer pinned to the bottom live in the center.
- The project inspector with General, Endpoints, Security, and MCP tabs lives on the right.
- The left and right panels are resizable, collapsible, and persist their layout locally.
- On narrow screens the side panels open as overlay drawers.
- A compact dark theme is used.

## Composer

- `Enter` sends the message; `Shift+Enter` adds a line; `Ctrl+Enter` queues it;
  `Ctrl+Alt+Enter` forks the branch and runs it immediately; `Ctrl+Shift+Enter` interrupts the
  current run and replies to the message first.
- During IME composition the message is not sent.
- After sending the composer is cleared and keeps focus.
- Streaming and Stop are implemented as a separate stage.
- The full "branch status × action" rules (Send/Queue/Fork, auto-Resume, pre-pause, prohibition
  of Edit&Replace during generation) — see [Composer rules](15-composer-rules.md).

## Input history

- `↑` on the first line opens the history of sent messages, `↓` on the last line returns to the
  newer ones. The key fires exactly on the edge line, not on the edge character: the entry is
  substituted with the caret at the end, and a requirement to reach position 0 would consume
  every second press on a single-line entry. Inside a multi-line entry the arrows still move
  between lines.
- The typed text is saved as position zero: `↓` past the newest entry returns it, `Esc` returns
  it immediately. While paging, the draft in localStorage is not rewritten — browsing history
  must cost nothing.
- Editing the substituted text detaches it from history: the counter goes blank, the text
  becomes a draft again, and the next `↑` starts the walk over from the newest entry.
- The `History N/M` counter sits in the status line above the field, `1/M` is the last sent
  entry. If the line is occupied by a Generating/Forking/Replacing chip, the counter becomes
  its muted prefix. The regular hint is not shown in that case.
- History belongs to the project, not the chat: formulations repeat ("run the tests", "do the
  recommended thing"), and they migrate between chats of the project. Only an accepted send
  (Send, Queue, Fork, Send now) lands there; a rejected one already stayed in the field.
  A repeat moves to the top instead of duplicating, 100 entries are stored in localStorage.
- The only key hint is `↑ for history` in the status line, when the field is empty and the
  history is non-empty. There is no history search (`Ctrl+R`) yet.

## Message queue

- The queue panel shows only what has not been sent yet. A sent command lives in the transcript,
  not in the list, every line of which would promise edit and delete.
- A stopped or failed run is shown as a chip at the end of the transcript, after the file-changes
  summary, together with Retry, Continue, From branch head, and Discard actions. The chip uses
  the same card as the changes summary. There is no chip for an ongoing generation: its timing
  and the Stop button already live in the composer, and a second copy added nothing.
- The `Queued · N` counter equals the number of visible rows, and `Clear` removes exactly those.
  The previous behavior depended on whether the worker was unwinding at that moment, so the
  same click produced different results. The separate "stop and clear all" action asks for
  confirmation.
- Any server rejection is shown to the user as the text the server returned. Earlier the client
  silently swallowed them, and the rejection was indistinguishable from inaction.
- Interruption preserves the already-written part of the answer as an incomplete message: both
  regular Stop and `Ctrl+Shift+Enter` behave the same way. A retry replaces this fragment with
  the full answer.
- An error stops the entire queue: the following messages usually depend on the previous answer.

## Endpoint profiles

- The project has a default endpoint, used automatically by new chats.
- A chat stores its own EndpointProfileId; changing the endpoint affects the next requests.
- The Endpoints editor uses master-detail: list on the left, the selected profile form on the right.
- Changes are applied explicitly through Save; Cancel returns the last saved state.
- Test connection performs a short model request and does not create a message.
- The credential is stored only in the protected Host store.

## Chats and branches

- New chat creates a UI draft; the document is saved after the first message.
- The chat has Rename, Duplicate active branch, and Delete.
- Only the active branch is shown in history; alternatives are switched near the branch point.
- Edit and branch creates a new branch, keeping the original message.
- Copy copies the source Markdown.
- Clicking the chat name in the sidebar, when one of ITS branches is already open, always returns
  to the primary/original branch — this is the only explicit way to get back to it (there is no
  separate "primary branch" row in the branch tree). Bug: `SelectChatAsync` restored the "last
  visited branch" for that chat EVEN when the chat was already open — `SelectBranchTreeItemAsync`
  had just written the current (non-primary) branch as the "last" one, so the restore immediately
  returned to it, and a repeated click on the chat name stopped doing anything. The "last branch"
  restore is now skipped if this chat was already selected immediately before the click — it is
  intended for a different case (entering the chat FROM OUTSIDE: from another chat or after a page
  reload), not for repeated clicking on an already open chat.

## Icons and feedback

- A local minimal set of Lucide SVG icons is used through a JavaScript-free Blazor component.
- Icon-only buttons carry an `aria-label`, tooltip, and focus state.
- The main Save/Delete actions keep their text label.
- Common results are shown as toasts; form errors sit next to the fields.

## Agent and MCP UI

- Tool calls of one agent step are grouped into a single collapsible card.
- An Ask approval is displayed inline with Allow once, Allow for chat, and Deny.
- File changes are shown as a linked Changes card with a unified diff for view only.
- These elements are implemented after the MCP connection manager and agent loop.

## Deferred

- Streaming, Stop, and incomplete responses.
- The full branch switcher and message action toolbar.
- MCP template library, approvals, and grouped tool timeline.
- FileSystem MCP changes/diff and native folder pickers.
- Search, export, and attachments.

## Implementation order

1. Workspace foundation: remove the prototype markup, inspector tabs, endpoint master-detail, default endpoint, Save/Cancel, toasts, and the minimum icons.
2. Layout and composer: resize/collapse, local layout, Enter/Shift+Enter, drafts, rename/delete.
3. Streaming.
4. Full branch UX.
5. MCP connection manager and agent loop.
6. FileSystem MCP, Changes, and diff.

## Implementation state as of 2026-08-12

The first working part of the workspace foundation has been implemented:

- the prototype markup has been removed from the DOM; the application uses a single three-panel workspace;
- the inspector is split into General, Endpoints, Security, and MCP tabs;
- Endpoints uses master-detail and explicit Save/Cancel;
- the project stores the default endpoint, and every chat stores the selected `EndpointProfileId`;
- a new chat inherits the project's default endpoint;
- the endpoint selection in the composer is saved immediately for the active chat;
- `Enter` sends the message, `Shift+Enter` adds a line, IME composition is not intercepted;
- the width of the left and right panels is changed by drag splitters and is persisted in `localStorage`;
- a local SVG icon set with `aria-label` and tooltip has been started.

Additionally implemented:

- the left and right panels collapse through icon-only buttons; the state is saved together with the layout width;
- the chat header gets buttons to restore the hidden panels;
- main successful operations and brief errors are shown through an auto-dismissing toast;
- `Test connection` performs a short real OpenAI-compatible completion through the Host gateway, uses the stored credential, and does not create messages in the chat history.

The streaming stage has been implemented:

- the Host requests OpenAI-compatible Chat Completions with `stream: true` and reads SSE `data` events up to `[DONE]`;
- credentials are resolved only on the Host and are not sent back into WASM;
- the assistant Markdown is rendered incrementally, and Send during generation is replaced with Stop;
- the user message is saved before the request; the completed assistant response is saved after `[DONE]`;
- a Stop or a stream break saves the already-received assistant response with the `Incomplete` flag;
- an empty partial assistant response is not created.

Not yet implemented in this stage: a full overlay drawer for both panels on mobile width and a specialized health-check, if a specific endpoint provides such an API.

The basic chat management stage has been implemented:

- New chat creates only a UI draft; the JSON document and the title from the first 48 characters are created on the first send;
- a chat can be renamed inline and deleted after a two-step confirmation in the header;
- Copy Markdown uses the Clipboard API and copies the source Markdown;
- Edit and branch moves the original user text into the composer and sets the branch point to its parent;
- near messages with alternative siblings a compact branch switcher appears;
- switching selects a sibling and continues its newest child path;
- Rename/Delete use revision and do not overwrite concurrent changes.

Duplicate active branch has not been implemented: it makes sense to add it together with export/import after the MCP agent loop.

## UX refinement: chat workspace

- The sidebar has only one clear Hide sidebar button; in the collapsed state only one compact icon-only Show sidebar control remains.
- In the chat header the endpoint selector sits next to the chat name and does not have a separate Configure button. Endpoint settings are available in the persistent right panel on the Endpoints tab.
- A draft chat does not show the artificial name `New chat`; the empty composer shows the disappearing placeholder `Message the assistant...`.
- Send sits in the bottom panel of the composer next to a hint about the available action; the icon and text explain the purpose.
- Project settings uses a fixed header and a danger zone pinned to the bottom, so Delete project does not change its position when switching tabs.
- Endpoints uses a profile picker and one convenient detail form, instead of two narrow simultaneously visible columns.
- The top bar of the center has been removed: the chat name is visible in the sidebar, and endpoint selection and editing are on the Endpoints tab on the right.

## Project settings placement

- The persistent right inspector panel has been removed: it took space from the chat workspace and mixed navigation with editing.
- The selected project has an icon-only `…` menu with the tooltip `Project menu` in the sidebar.
- The menu contains `Project settings`, which opens a modal tabbed window, and `Delete project` with an inline confirmation in the same menu.
- In editable tabs `Save` saves and closes the window, `Cancel` rolls back the draft and closes. The separate `X` button has been removed as a duplicate action; a click on the dimmed background is equivalent to Cancel.
- The Project settings modal size is fixed for all tabs; when the viewport height is insufficient, only the contents of the active tab scroll.
- `Save` and `Cancel` are shared across all tabs and pinned to the dialog footer; switching the tab does not change their position. Contextual actions, such as `Test connection`, stay inside the corresponding tab.
- The dialog uses an enlarged fixed size of `42rem × 52rem`, but is always constrained by the available viewport. Internal scrolling remains a fallback only for small screens or longer content.
- Adding and removing endpoints is done through compact `+` and `−` buttons next to the profile picker; the full purpose of the buttons is available through tooltip and accessibility label.
- The sidebar does not show separate product branding: the space starts right away with the navigation sections. Collapsing the entire sidebar at once is supported by **one** toggle button `.sidebar-toggle`: in the expanded state it shows `chevron-left` with the tooltip `Hide sidebar`, in the collapsed state — `chevron-right` with `Show sidebar`. This is literally "one button replaces another" from the decision above, not two separate buttons in the same position. The collapsed sidebar shrinks to `2.8rem` (`--sidebar-track`); its content and the left resizer are muted through `visibility: hidden; pointer-events: none`. Collapsing the entire panel coexists with collapsing the individual Settings/Projects sections — these are independent mechanics, like width adjustment by dragging `.workspace-resizer[data-side="left"]`.
- The `.sidebar-toggle` button is moved out of `.workspace-sidebar` and positioned absolutely relative to `.workspace-shell` (which gets `position: relative` for this), with horizontal anchoring to the track width: `left: calc(var(--sidebar-track) - 2.5rem)`. This way the same CSS declaration gives the correct place in both states (at the right edge of the expanded sidebar and at the center of the collapsed strip), and the button does not reserve vertical space above the chat area. Keeping it inside `.workspace-sidebar` is not allowed: it has `overflow-y: auto`, so an absolute child at the right edge would be clipped by the scroll container and would scroll away together with the content.
- The collapse state lives in C# (`_isSidebarCollapsed`); the `left-collapsed` class is bound on `<main>`, is persisted under a separate `localStorage` key (`ai-client.sidebar-collapsed.v1`), and is read once on `firstRender`. The layout JS module no longer manages classes — it is responsible only for width dragging; this removes two owners of one state.
- The sidebar consists of two root, independently collapsible sections — **Settings** (`Connections`/`Security`/`MCP`) and **Projects** (the list of projects and their chats). Each section is a `.sidebar-heading` with a heading button `.sidebar-heading-toggle` (chevron + label), a click on which toggles `_isSettingsSectionExpanded`/`_isProjectsSectionExpanded` and expands/hides the section content; the chevron rotates 90° through `[aria-expanded="true"] .app-icon { transform: rotate(90deg) }`. `New project` (`+`) remains a separate button next to the `Projects` heading outside the collapsible area and **automatically expands** the Projects section after creating a project — otherwise a new project would be created and selected, but invisible in the collapsed list.
- The defaults are intentionally different: **Settings is always collapsed** by default (`_isSettingsSectionExpanded` without initializer, `false`), **Projects is always expanded** by default (`_isProjectsSectionExpanded = true`) — Projects is the main working context, Settings is a secondary area. Neither is persisted (no localStorage) — every application reload returns the state to these defaults.
- In "phone" mode (`width <= 720px` — the same breakpoint already used in `@media (width <= 720px)` for the sidebar/content stack) both sections are automatically collapsed, even if the user expanded them. This is implemented through `window.matchMedia('(max-width: 720px)')` in `workspaceLayout.js:watchPhoneMode`, which checks `query.matches` immediately on attach (a page loaded in a narrow viewport immediately receives collapsed sections) and listens for `change` for live resizing; in both cases it calls `[JSInvokable] Home.OnEnterPhoneMode()` through `DotNetObjectReference`, which resets both flags to `false` and calls `StateHasChanged()`. The transition back to desktop width does not automatically expand the sections — the user returns to the regular defaults only on the next full reload.
- In phone mode the sidebar is always expanded, and the `.sidebar-toggle` button is hidden (`display: none` inside `@media (width <= 720px)`): in the vertical layout the panel already occupies the full width above the chat, so there is no point in collapsing it to a `2.8rem` strip. `OnEnterPhoneMode()` additionally resets `_isSidebarCollapsed` to `false` — the state is brought into correspondence with reality, not just overridden by styles, otherwise a flag saved from desktop would leave the sidebar contents hidden (`visibility: hidden` from `.left-collapsed`) while the expand button is unavailable. For the same reason, `LoadSidebarCollapsedAsync()` is called BEFORE `WatchPhoneModeAsync()`: otherwise loading a saved `true` would happen after the reset and would collapse the panel again on phone.
- The tradeoff is consciously accepted: on the first application load (outside phone mode) the active project and its chats are selected automatically (as before) and immediately visible thanks to the default-expanded Projects; in phone mode the same selection happens, but the list is visually hidden until the user expands the section manually — collapsing affects only the visibility of the list in the sidebar, not the internal state selection.
- Когда навигация не видна (свёрнута секция Projects **или** свёрнут весь sidebar) и выбран проект, над лентой чата показывается компактный `.conversation-context-header` вида `Проект › Ветка` через разделитель-шеврон — иначе пользователь не видит вообще, что сейчас открыто. Условие именно «ИЛИ» по двум независимым механикам сворачивания: свёрнутый sidebar прячет и развёрнутую секцию Projects тоже. Когда навигация видна, заголовок не нужен и не показывается — сайдбар и так показывает выбор через `.selected`.
- Второй элемент хедера — именно **активная ветка**, а не чат. У главной («корневой») ветки нет собственного имени: `GetBranchTreeItems()` возвращает только ответвления от форков, а роль главной ветки играет сам чат — поэтому `GetContextBranchTitle()` подставляет туда название чата. Так хедер всегда состоит ровно из двух элементов и на любой ветке показывает то же имя, что подсвечено в дереве sidebar. Активная ветка определяется через `GetSelectedBranchItem()` — самое глубокое ответвление, содержащее текущий `_branchLeafId`; ранее эта логика жила внутри `GetSelectedBranchId()`, теперь `GetSelectedBranchId()` выражен через неё, чтобы порядок выбора ветки не дублировался в двух местах.
- Composer textarea авто-расширяется по высоте по мере ввода (по образцу поведения из Codex): JS `chatComposer.js:attach` слушает `input`, выставляет `height:auto`, затем `height:scrollHeight+px`; CSS `max-height:40vh` + `overflow-y:auto` ограничивают рост и включают внутренний скролл, когда содержимое не помещается. `resize:none` — пользователь не может вручную тянуть за угол (это конфликтовало бы с авто-высотой). Возврат к `min-height:4.5rem` после программной очистки/подстановки `_chat.Message` (отправка сообщения, "Edit and branch", удаление активного чата) — через флаг `_composerNeedsResize`, проверяемый в `OnAfterRenderAsync` (тот же паттерн, что уже применяется для `_scrollMessagesToBottom`): JS `resize()` обязан читать `scrollHeight` уже ОТРЕНДЕРЕННОГО Blazor'ом значения textarea, а не измерять высоту сразу внутри C#-обработчика — вызов сразу после присваивания `_chat.Message` мог бы измерить старое, ещё не обновлённое в DOM содержимое, поскольку JS interop может выполниться до того, как Blazor допишет рендер.
- Слева от текста чата показывается полоса маркеров истории (`.history-markers`) — навигация ВНУТРИ одной ветки; навигация между чатами и ветками остаётся в sidebar. Полоса лежит в левом жёлобе центрированной колонки сообщений и позиционируется абсолютно внутри `.messages-area`, поэтому не сдвигает текст. Ширина подобрана так, чтобы влезать даже в минимальный жёлоб `2rem`: при viewport 820px полоса заканчивается на 270px, текст начинается на 276px.
- Раскладка меток равномерная — один слот на сообщение (а не пропорционально высоте прокрутки). Текущая позиция показывается «рыбьим глазом» через `scaleX`, но по-разному в двух режимах: пока пользователь не наводит курсор, пик определяется прокруткой (дискретно, по индексу соседних сообщений, диапазон 0.4–1.0). При наведении курсор сам гнёт полосу — пик следует за курсором непрерывно по пиксельной дистанции (радиус ~70px, квадратичное затухание), и амплитуда примерно вдвое больше (0.15–1.45), потому что жест мыши — это явное «посмотри сюда», а не фоновое состояние. У пика при наведении также появляется тултип с превью текста сообщения (`.history-marker-tip`), позиционированный на этом же сообщении.
  - `transform-origin` у метки — `center`, не `left`: при амплитуде наведения пик может превышать 1.0, и если бы рост шёл только вправо, на узком экране (жёлоб `2rem`) он бы упёрся в текст сообщения. Центрирование делит рост пополам — половина уходит влево, в пустое пространство жёлоба, — и на измеренном худшем случае (viewport 820px, жёлоб 32px) оставляет запас ~2px до текста вместо отрицательного. Отсюда же взят потолок амплитуды 1.45, а не буквально 1.6: на этом самом узком экране разница между «безопасно» и «залезает под текст» — доли пикселя.
  - Роль кодируется яркостью (пользователь светлее), состояния — цветом существующей палитры (генерация, непрочитанное, незавершённое, ошибка), точка ветвления — не вторым штрихом, а короткой вертикальной засечкой слева от основной полоски (`::after`, `left:0`, `.history-marker-fork::before` сдвинут вправо через `margin-left`, чтобы место под засечку не перекрывалось). Засечка вертикальная, а не диагональная: диагональная линия визуально перекашивалась бы при горизонтальном `scaleX`, вертикальная от этого не искажается, только сдвигается по X вместе с ростом полоски.
  - Полоса прокручивается сама, своего скроллбара не показывает (`scrollbar-width: none`), нативный скроллбар ленты остаётся справа.
- Полоса скрывается, когда лента помещается на экран целиком (класс `idle`) и в phone-режиме, где жёлоба нет. Метки не фокусируются (`tabindex="-1"`, `aria-hidden` на полосе): дублировать навигацию 200 таб-стопами вредно, доступная навигация остаётся в sidebar и в самой ленте.
- Группа меток центрируется по вертикали (`justify-content: safe center`), промежуток между метками `0.55rem`. Сама кнопка-метка имеет высоту `0.7rem` и служит зоной попадания, а видимый штрих рисует `::before` высотой 2px — иначе целиться пришлось бы в 2-пиксельную линию. Ключевое слово `safe` нужно, чтобы при переполнении центрирование не срезало начало списка.
- CSS `:hover` на самой наведённой метке остаётся отдельно от JS fisheye и реагирует цветом (белый) и небольшим утолщением штриха/засечки — это не конфликтует с непрерывным ростом от курсора, а дополняет его точечным акцентом на буквально наведённом элементе. Цвет метки задаётся свойством `color`, а штрихи рисуются `currentColor`.
- Цвета состояний объявлены с удвоенным классом (`.history-marker.history-marker-failed`), чтобы перебивать `.active` и `:hover`. Иначе метка с ошибкой, до которой пользователь просто доскроллил, становилась бы белой и переставала читаться как ошибка.
- Масштаб метки задаётся инлайновым `transform: scaleX()` из JS, а не `width` и не через `var()` в CSS: `transform` не трогает layout, поэтому прокрутка и наведение не вызывают reflow. Активная позиция вычисляется по `offsetTop` сообщений, закэшированным до изменения `scrollHeight`, — чтобы обработчик прокрутки не измерял все сообщения на каждый кадр. Края закреплены явно: в самом верху активна первая метка, в самом низу — последняя, иначе якорь «четверть экрана» промахивается мимо крайних сообщений.
- `render()` в `historyMarkers.js` вызывается из `scroll`/`mousemove`/`mouseleave` НАПРЯМУЮ, без `requestAnimationFrame`. Первая версия оборачивала его в rAF (стандартная практика для троттлинга частых событий), из-за чего пользователь сообщил, что fisheye по курсору не отображается вовсе. Диагностика (клик по метке работал, значит `attach()` отработал и слушатели живы; синтетический `mousemove` без rAF-обёртки — через прямой вызов `refresh()` — тоже работал) показала, что именно rAF-колбэк не срабатывал. Причина не в самом коде, а в том, что `requestAnimationFrame` не гарантированно выполняется в ряде обычных ситуаций (окно не в фокусе, энергосбережение, фоновая вкладка) — эффект, который работает не всегда, хуже эффекта, который стоит чуть больше CPU на десяток кнопок. Побочно тем же тестом подтверждено, что пересоздание DOM-узла `<nav>` (например, при переходе в Settings и обратно) не ломает переподключение — `SyncHistoryMarkersAsync` в `Home.razor` корректно вызывает `attach()` заново, когда секция снова становится видимой.
- Тултип метки (`.history-marker-tip`) живёт как сосед `.history-markers`, а не внутри неё: изначально он лежал внутри ленты и позиционировался через `left: calc(100% + 0.5rem)` относительно неё, но `.history-markers` использует `overflow: hidden auto` (нужен для собственного скролла ленты), и это же правило обрезало тултип, вылезающий за правый край ленты по X — поэтому он никогда не был виден, при любом наведении.   - Второй источник мигания — смена строки с «крутится» на результат: иконка меняется, а справа внезапно возникают summary и длительность. `tool-row-resolved` даёт им fade 120мс, и ставится только тем строкам, которые пользователь застал в состоянии running (`_pending` → `_resolved`); строка, отрисованная уже завершённой, ничем не мигает и остаётся неподвижной при разворачивании готовой группы.
- Только `IsIncomplete` относится к конкретному сообщению; статус run описывает ветку целиком, поэтому его цвет вешается на последнее сообщение ветки, а генерация — на отдельную метку стримящегося ответа. Это осознанная аппроксимация, а не точное соответствие.
- `.workspace-conversation` — grid из четырёх явных строк (`auto minmax(0,1fr) auto auto`): header (1), `.workspace-messages` (2), `.composer-status` (3), `.workspace-composer` footer (4) — у всех четырёх элементов проставлен явный `grid-row`, ни один не полагается на позиционный auto-placement. Причина: header рендерится условно (только когда Projects свёрнута); когда его нет в DOM, авто-размещение отдавало освободившуюся первую строку (`auto`) первому auto-позиционированному ребёнку по document order — а это оказывался `.composer-status` ("Continuing selected chat"/"A new chat will be created on send"), из-за чего при развёрнутой (дефолтной) Projects этот текст ошибочно уезжал в самый верх чата вместо места над composer'ом внизу. Явный `grid-row` на всех четырёх элементах делает раскладку детерминированной независимо от того, рендерится ли header.
- `.workspace-sidebar` имеет `overflow-y: auto`. В phone-режиме sidebar ограничен `max-height: 13rem` и стоит НАД лентой чата (`grid-template-rows: auto 1fr`); если развёрнутые Settings+Projects с несколькими чатами превышают эту высоту, без `overflow` содержимое визуально вылезало за пределы своего блока и накладывалось на текст чата снизу (а не обрезалось/скроллилось). `overflow-y: auto` заставляет sidebar скроллиться внутри себя вместо наложения на соседний контент.
- Подсветка `.selected` у строки проекта и строки чата в sidebar учитывает `_globalSection is null`, а не только совпадение `Id` с `_selectedProject`/`_selectedChat`. Переход в глобальную секцию (`Connections`/`Security`/`MCP`) не сбрасывает `_selectedProject`/`_selectedChat` (это разные, независимые состояния — активный проект/чат остаются "в фоне", чтобы вернуться к ним при закрытии Settings), поэтому без этой проверки строка активного проекта и чата продолжали визуально подсвечиваться как выбранные ОДНОВРЕМЕННО с выбранным пунктом Settings, хотя в основной области отображается только один из них. Выделено должно быть ровно то, что показано в основной области — не более одного пункта сразу.
- Chat создаётся лениво при первой отправке сообщения внутри выбранного проекта. Отдельное действие `New chat` начинает ещё один разговор, но не является обязательным для первого разговора проекта. Невалидная конфигурация endpoint всегда приводит к видимому сообщению, а не к тихому отказу.
- Контекстные действия проекта показываются справа от выбранного проекта как icon-only кнопки с SVG и tooltip: создание чата и настройки. Отдельной глобальной кнопки `New chat` нет. Отправка сообщения использует круглую светлую кнопку со стрелкой вверх.
- Контекстные меню проекта и чата закрываются кликом вне меню. У каждого чата есть компактное меню с удалением и обязательным inline-подтверждением; удаление активного чата возвращает центральную область в состояние начала нового разговора.
- Все кнопки используют единую нейтральную тёмную visual language кнопки настроек. Форма может отражать назначение элемента (icon-only, text или round Send), но фон, рамка, hover, focus и disabled states согласованы; красный используется только для destructive actions.
- Кнопки в состоянии покоя полностью плоские: без видимой рамки (`border: 1px solid transparent`) и без непрозрачного фона (базовое правило `button` больше не задаёт `background`). Ранее resting-фон `#2b2b2b` на каждой кнопке визуально читался как "рамка"/бокс вокруг обычных nav-элементов и текстовых кнопок (например, `Save`/`Cancel`) даже без реального `border` — именно это и было устранено. `.secondary-action` (`Cancel`) также лишилась собственных resting `background`/`border-color`, которые независимо от базового правила давали видимый бокс.
- Единый акцентный цвет выделения — `--accent-color: #7eb4ed` (CSS-переменная в `:root`). Используется для: hover-цвета текста/иконки любой кнопки (`button:hover`), `button:focus-visible` outline, подсветки выбранной ветки сообщения (`.chat-response.selected-branch`, `.branch-switcher button.selected`), рамки/box-shadow активного (`:focus-within`) composer'а (было нейтральное серое `#686868`). Это единая точка правды для "цвета выделения" в приложении — новые состояния выделения/hover/focus должны ссылаться на `var(--accent-color)`, а не заводить свой оттенок синего или серого.
- Строки веток в sidebar окрашены так же, как чаты (`#b9b9b9` от `.chat-link`), а не собственным цветом. Ранее `.branch-link` делил legacy-правило с ныне мёртвым `.link-danger` и тянул из него жёстко прописанный `#8ab4df` — это был третий оттенок синего, не совпадающий с `--accent-color`, из-за чего все ветки выглядели постоянно выделенными и конкурировали с акцентом. Теперь синим (`var(--accent-color)`) ветка становится только на hover, а активная выделяется фоном `#2b2b2b` через общий `.chat-nav-row.selected`.
- Персистентные (не-hover) состояния `.selected` — активный проект/чат в sidebar (`.project-nav-row.selected`, `.chat-nav-row.selected`), активная глобальная секция (`.global-nav .selected`), выбранная вкладка настроек (`.settings-tabs button.selected`), выбранный connection/endpoint (`.settings-list button.selected`) — сохраняют собственный явный серый фон отдельными правилами; это осознанно НЕ тронуто в этом проходе (они не "рамка кнопки без hover", а постоянный индикатор текущего выбора, который должен быть виден и без наведения мыши).
- Акцентные destructive-кнопки (`.danger`, `.menu-danger`, endpoint remove) и Send сохраняют собственные цветные hover-стили (фон/рамка) как документированное исключение из плоского/акцентного языка — сброс общего hover-цвета потребовал явно прописать им `color` на hover, иначе базовое правило перекрашивало текст/стрелку в акцентный синий поверх их цветного фона (для Send это делало бы стрелку плохо читаемой на светлом hover-фоне).
- `.project-nav-row` использует `gap` между дочерними кнопками (текст, `+`, `⋮`) вместо `margin-right` на конкретной кнопке — asymmetric margin на `.project-menu-button` ранее сдвигал её kebab-иконку относительно `.chat-menu-button` в списке чатов на ту же величину margin, из-за чего кнопки `⋮` проекта и чата не выстраивались в один столбец.
- Send является акцентным исключением из нейтральной тёмной палитры: доступная отправка имеет светлый фон и тёмную стрелку, а недоступная — явно тёмное приглушённое состояние. Hover и active должны быть визуально различимы.
- Состояние Send обновляется на каждый вводимый символ. Потеря фокуса composer не требуется для активации кнопки или отправки по клавиатуре.
- Сообщения не имеют повторяющихся role labels `User` и `Assistant`: их сторона и оформление задают контекст. Текущий статус (`Generating...`, новый или выбранный чат) показывается непосредственно над composer; исключение — локальная метка `Incomplete` для незавершённого сохранённого ответа.
- При открытии чата и поступлении streaming response история автоматически следует за последним сообщением. Прокрутка выполняется после рендера DOM, поэтому учитывает фактическую высоту нового Markdown-содержимого.
- Streaming завершается по `[DONE]` или `finish_reason`. Поток, который после начала ответа молчит дольше idle timeout (`IChatTransportPolicy.StreamIdleTimeout`, 60 секунд), считается оборванным и завершает ран ошибкой, а не готовым ответом: раньше 10-секундный fallback принимал обрывок вроде «Сразу создаю файлы.» за весь ответ модели, которая просто думала перед вызовом инструмента, и ран отчитывался об успехе с несделанной работой.
- Для idle timeout событием считается любое SSE-событие `data:`, включая дельты рассуждения (`reasoning_content`), которые в ленте не показываются. Transport keep-alive, SSE comments и пустые строки не продлевают состояние генерации.
- Меню проекта и чата используют единый вертикальный kebab glyph (`⋮`, три точки, без обводки для чёткого рендера на маленьком размере); назначение конкретной кнопки уточняется tooltip и accessibility label. Координаты точек (`cy = 6/12/18` в 24-unit viewBox) подобраны так, чтобы при масштабировании до фактического размера иконки (16px) все три центра попадали на целые пиксели — иначе субпиксельное сглаживание крайних точек создаёт иллюзию, что они не строго друг под другом.
- Пункты меню проекта и чата сопровождаются векторной иконкой (`sliders` для Project settings, `trash` для Delete project/Delete chat) слева от текста. `sliders` (три вертикальные линии с горизонтальными ручками) выбран вместо шестерёнки `settings` по образцу референса пользователя.
- Меню проекта и чата дополнительно открываются правым кликом (`contextmenu`) по строке проекта или чата — с тем же поведением, что и клик по kebab-кнопке; правый клик по невыбранному проекту сначала выбирает его, затем открывает меню.
- Полноэкранный `context-menu-backdrop` перехватывает правый клик поверх других строк, пока меню открыто. Чтобы правый клик по чату при открытом меню проекта закрывал старое меню и сразу открывал меню чата (а не системное контекстное меню браузера), backdrop сам обрабатывает `contextmenu`: закрывает текущее меню и через `WorkspaceLayoutService.ForwardContextMenuAsync` (JS `workspaceLayout.js:forwardContextMenu`) переигрывает событие на элемент под курсором, temporarily отключая `pointer-events` backdrop'а.
- Лента сообщений компактна: вертикальный отступ между сообщениями ~11px (было ~1.5rem margin + зарезервированное место под `.message-actions`), паддинг `workspace-messages` уменьшен с `2rem` до `1.1rem`, паддинг user-пузыря — с `0.8rem 1rem` до `0.55rem 0.9rem`. Кнопки действий под сообщением (`.message-actions .icon-action`) уменьшены до `1.6rem`, так как `opacity: 0` не убирает их layout-высоту — при исходном размере `2.25rem` они резервировали заметный пустой зазор под каждым сообщением даже без наведения.
- Kebab-кнопка чата (`.chat-menu-button`) скрыта (`opacity: 0`) в состоянии покоя и появляется по hover/focus строки (`:hover`, `:focus-within`) или пока меню открыто (класс `.menu-open`) — тот же паттерн, что уже использовался для `.message-actions`. Кнопка меню проекта остаётся всегда видимой (совпадает с существующим поведением, менять не просили).
- Список чатов проекта поддерживает клавиатурную навигацию: `ArrowUp`/`ArrowDown`/`Home`/`End` на любом сфокусированном элементе внутри `.workspace-chat-list` переводят фокус между `.chat-link` кнопками через `WorkspaceLayoutService.FocusAdjacentItemAsync` (JS `workspaceLayout.js:focusAdjacentItem`); `Enter`/`Space` работают нативно на сфокусированной кнопке без дополнительного кода.
- Проекты и чаты внутри проекта поддерживают drag-and-drop reorder (нативный HTML5 DnD на `.project-nav-row`/`.chat-nav-row`). Порядок — **client-side, per-browser**: сохраняется в `localStorage` (`ai-client.project-order.v1`, `ai-client.chat-order.v1.{projectId}`) и накладывается на список после каждой загрузки с сервера (`ApplyProjectOrderAsync`/`ApplyChatOrderAsync` в `Home.razor`), а не персистится в домене/API. Осознанный компромисс: domain/API/JSON-хранилище сегодня вообще не имеют понятия порядка (проекты сортируются по `Name`, чаты — по `UpdatedAt desc`), и добавление персистентного `SortIndex` через Domain/Infrastructure/Contracts/Host было бы значительно большей задачей. Ограничение: порядок не синхронизируется между браузерами/устройствами и не переживает смену браузера. Если нужен серверный reorder — потребуется отдельная доработка (новое поле `SortIndex` в `Project`/`ChatThread`, bulk reorder endpoint, обновление `ProjectDocument`/`ChatDocument` сериализаторов).

- В Connections и MCP кнопка `−` (Remove) стоит НАД списком, кнопка `+` (Add) — ПОД списком (`.settings-list-column`, grid `auto minmax(0,1fr) auto`), вместо обеих кнопок вместе в `.global-header`. Раньше `.global-header > div:last-child` заодно случайно ловил единственный `<div>` заголовка Security (у него нет второго div с кнопками — `:last-child` при одном ребёнке совпадает с ним же), превращая `<h1>Security</h1><p>...</p>` в flex-row с `justify-content: space-between` — из-за этого подсказка отображалась не под заголовком, а сбоку/в другом месте строки. После переноса кнопок Add/Remove из `.global-header` в `.settings-list-column` у ВСЕХ трёх секций (`Connections`/`Security`/`MCP`) в header остаётся только один `div`, поэтому фрагильный селектор `:last-child` просто убран из общего правила (оставлен только для `.section-heading`, где два ребёнка — это осознанный, стабильный контракт).

- `Connections`, `Security`, and `MCP` are permanently visible in the upper part of the sidebar and replace the chat in the central area.
- Connections use a two-pane editor: list on the left, form on the right, with shared `Save`/`Cancel`.

## Branch tree in the chat list (2026-08-13)

- A chat without alternatives remains one regular row. The selected chat expands its branch rows; other chats remain collapsed.
- A branch is represented as a nested chat-like row with a tree connector and an SVG branch icon. All logical levels are retained, while visual indentation stops growing after level three.
- The branch title is derived from its first new user message (up to 48 characters). An empty fork is not shown until that message is sent.
- Selecting the root chat always opens its original path. Selecting a nested branch opens that branch's latest descendant.
- The original path is not duplicated as a nested branch row; only alternatives are shown below the root chat.
- Project, chat, and branch names support the same inline rename flow: Rename from the row menu, Enter or blur to save, Escape to cancel.
- Deleting a branch removes that branch and every descendant. If it was open, selection moves to the nearest surviving parent.
- User messages have a compact `Edit and replace branch` action. It loads the message into the composer; sending atomically removes that message and its descendants, then writes the edited message from the same parent. Cancel leaves history unchanged.

## Calmer sidebar run-status indicators (2026-09-14)

- The `run-status-generating` colour is a static bright white — no looping opacity animation, on the icon or the `status-dot`, and no longer green (green is reserved elsewhere, e.g. the queue resume action). The prior "breathing" animation (a softer replacement for an earlier hard on/off blink) still read as distracting while working continuously in the chat, so the fix is to stop animating this state at all rather than tune the curve again.
- A project row shows no status dot while that project is the currently selected one — its chats are listed right below it, so the aggregate dot would just repeat what's already visible per-chat.
- A chat row (or branch row) that is currently open in the transcript hides completed/unread/attention statuses — the message feed already shows those. Generating is the one exception and stays visible even for the open chat/branch, since it's live progress rather than a state the user has already seen and dismissed.
- When a collapsed project needs to represent several chats with different statuses, the one shown is picked by urgency: Failed > needs attention (pending approval / paused / interrupted) > unread completion > generating. An outright failure always wins even over a merely-paused run, since it is the state most likely to need the user to act. See `GetProjectRunPriority` in [Home.razor](../src/AI.Web/Pages/Home.razor).
- The message-branch picker inside a message (the sibling-branch dropdown in `MessageFeed.razor`) follows the same rule for its own status dots: the currently active option's status is suppressed unless it's Generating, since its content is the transcript rendered right below the picker.
- **Attention (yellow) must actually clear once visited, not just while the chat is currently open.** `NeedsAttention` (pending approval / paused / interrupted / failed-with-recovery) used to short-circuit `GetStatusClass` unconditionally, so visiting a chat only hid the badge for as long as it stayed selected — leaving it re-appearing everywhere else (sidebar, project aggregate) the moment the user navigated away, since the underlying `Status` field never resets. Fixed by splitting the concept in `RunStatusPresentation`: a live block (`PendingApproval`) always shows, since the run genuinely cannot proceed; a dormant one (Paused/Interrupted/Failed-with-recovery) now shows only while `HasUnreadResponse` is true — the same "seen it, stop nagging" rule a plain unread completion already followed — via the new `HasVisibleAttention`. Visiting the chat calls the existing `MarkSelectedChatReadAsync`, which clears `HasUnreadResponse` on the server, so the badge disappears for good (until the run enters that state again), not just while looking at it.

## Chat list paging and loading placeholders (2026-09-16)

- The chat list shows one page of 10 chats, with a `Show N more` action that reveals the next 10 and a `Less` action back to the first page. A long-lived project otherwise pushes the directory group and everything under it off-screen. The paging window is per-project and survives background refreshes of the same project; switching projects starts over at one page.
- The open chat is never paged away: the window stretches to include it. It carries the branch tree and the selection highlight, so hiding it would make the sidebar disagree with the transcript on screen.
- A hidden chat whose run wants attention (generating / unread / pending approval) is counted on the `Show N more` action as a badge, in the same shape as the per-chat branch count. Paging may hide a row, but it must not hide the fact that something happened below the fold.
- Loading shows placeholder rows carrying the real row geometry (mark slot, then label), not a `Loading...` line. The text line sat above an empty sidebar and was then replaced by the list, so every start shifted the layout; the placeholder arrives in the shape the content will take.
- Placeholders are damped at both ends by `DelayedBusyIndicator`: nothing is shown for the first 150 ms of a load, and once shown it stays for at least 300 ms. The gateway is local and usually answers in tens of milliseconds, so an honest flag flashes for two frames and reads as a rendering glitch.
- A placeholder replaces content only when there is none. A background refresh of a list the user is already reading keeps the list — including the project list, which is now fetched into a local and swapped in, instead of being cleared before the request.
- Projects and chats load under separate indicators. The project list arrives in one request while its chats only arrive after the project's settings round-trip, and holding the whole sidebar until the slower of the two was what made the wait feel long. The project list is therefore rendered and clickable while the chat list is still placeholder rows.
- Selecting a project clears the previous project's chats immediately. They used to stay on screen, listed under the new project's name, until the new list arrived.

## Chat switching: cancellable, and rendered tail first (2026-09-16)

- Measured first, on a real project of 25 chats: the server answers a chat request in 10–40 ms, deserialising its JSON costs 5–70 ms, and rendering the transcript (Markdig plus HtmlSanitizer) costs 150–550 ms on desktop JIT — several times that in the browser's interpreter, since the Web project is not AOT-compiled. The delay between clicking a chat and seeing it is therefore almost entirely client-side rendering, not the network.
- Opening a chat is cancellable and last-click-wins. Every selection carries a `CancellationTokenSource`; a newer click cancels the older one, its HTTP request is abandoned rather than deserialised, and each `await` is followed by a guard so an abandoned selection cannot write selection state. Before this, two quick clicks raced and the slower response could land last, leaving the wrong transcript open.
- The sidebar highlight follows the click, not the data. `_pendingChatId` is set synchronously, so the row is selected within ~15 ms while its transcript is still loading; a click no longer looks ignored for the length of a render.
- Marking a chat read and recording "where I was" happen after the render that shows the transcript, not before it. They are a server round-trip and a storage write, and neither changes what is on screen.
- A transcript opens at its tail: the last 10 feed items render first, the rest one frame later. Measured on a 160-message branch: first content at ~0.5 s instead of ~1.6 s. The limit is decided in `OnParametersSet`, not while rendering — it is passed to `TranscriptRenderBoundary` as a parameter, and a parameter set during the render reaches the boundary a render too late, which leaves the transcript permanently truncated.
- The scroll anchor is suspended while a remembered position is being restored. Anchoring exists to hold the transcript still when content appears above it, which is exactly what the expansion does, so left on it measures the drift the restore itself introduced and undoes it.
- `historyMarkers.js` advances its restore loop on a timer when frames stop coming. `requestAnimationFrame` does not tick in a tab that is not being painted, and the loop — which re-applies the scroll target until the height settles — would otherwise never finish, leaving both the feed and the caller's await hanging.
- Five transcripts stay warm instead of two, in both the chat-details cache (`Home`) and the rendered-markdown cache (`MessageFeed`). Returning to a recently visited chat renders from cache in ~0.1–0.4 s; the cost is memory, and five is the point where a realistic back-and-forth is covered without pinning a whole project's history in the browser.

## Message toolbar: off the text, with Comment (2026-09-28)

- A question's toolbar sits beside the bubble, in the empty space on its left, not over its corner, vertically centred on the bubble's last line. Answers do the same in their own corner: sat on the article's bottom edge, the taller buttons and the leaf's bottom padding put the chip below the text. The chip takes the text's font, so `1lh` is that line; `--message-padding-end` carries the bottom padding (`.branch-leaf` trims it), and a branch switcher row is added on top. Over the corner it covered a short question whole, and with it the text a comment is made by selecting. It still takes no height. When the feed is under 30rem wide (a container query on `.workspace-messages`) there is no room beside the bubble, so the chip straddles the bubble's top edge as a pill instead.
- A Comment button opens the review comment editor from the toolbar: on the user's selection if it is inside the message, otherwise on the whole message (up to the 2000-character quote limit; longer messages ask for a selection). The editor still opens from a selection; the button only makes one and replays the mouseup.
- A question's toolbar is Copy, Comment, Edit and branch, More. Fork from here and Edit and replace branch moved into More (a popover pinned to its button by `messageActions.js`). The destructive action is the menu's last item, after a separator, and the only one in colour. Answers keep Copy, Comment, Fork.
- All toolbar icons share one muted colour and brighten on hover. Copy turns into a check for 1.2 s.

## Chat list order: manual for pinned, activity for the rest (2026-09-28)

- Pinned chats keep the order the user gives them; nothing that happens in a chat moves one. The rest follow activity, newest first, so a chat with a new message or reply rises to the top of that zone, and a new chat appears first under the pinned ones. Dragging an unpinned chat among the unpinned ones does nothing, because the next message would undo the position anyway.
- Activity is the user's message, the end of a reply (including a partial one saved on interrupt) and a failed run. Tool calls and their results do not count: a long run otherwise kept jumping its chat to the top on every step. Renaming, pinning and comments never counted. A failure writes no message, so the Host records the moment on the chat (`ChatThread.MarkActivity`) and the document keeps it.
- The order of pinned chats is a fractional key per chat (`IPinOrderKeys`, base-62, compared ordinally): a move rewrites only the moved chat. Chats pinned before this existed have no key and come first, in the order they were pinned; they get keys the first time something is placed in front of one of them.
- Drag and drop uses pointer events, not the HTML5 API, which has no touch support and no control over the drop line (`chatListDrag.js`). The whole row is the handle; a mouse drag starts after 5 px so a click still opens the chat, and on touch a 400 ms long press starts it while an earlier move stays a scroll. A thin divider closes the pinned zone: a drop above it places the chat in front of the row under the line, pinning it if needed; a drop below it unpins. With nothing pinned, a dashed "Drop here to pin" zone appears at the top while dragging. The ghost says Pin or Unpin when the drop would change that. `Esc` cancels, the list scrolls at its edges, and holding over "Show N more" opens the next page.
- Pinning from the button, the menu or `Alt+P` puts the chat last among the pinned ones, so the order already given stays. `Alt+↑`/`Alt+↓` move a focused pinned chat within the zone and announce the new position; there are no Move up/down menu items.
- The list re-reads its order when a run in the project starts or ends, not only after the user's own actions. While a mouse is over the list or a chat is being dragged the new order waits and is applied when the pointer leaves, so no row moves under the cursor. Rows that move slide to their new place (FLIP, 180 ms, off under reduced motion).
- A chat without messages stays out of the list until its first message, whoever created it; the open chat is the exception, because its first message may still be on the way to the Host when the list is re-read.
