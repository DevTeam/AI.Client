# Composer: правила отправки, очереди и ветвления

Статус: Accepted baseline

Источник истины для поведения composer'а (кнопка Send / Ctrl+Enter / Ctrl+Alt+Enter / Edit&Branch /
Edit&Replace / Fork from message). Реализация — [`ChatComposerService`](../src/AI.Client.Web/Composer/ChatComposerService.cs),
тесты — [`ChatComposerServiceTests`](../tests/AI.Client.Web.Tests/Composer/ChatComposerServiceTests.cs).
При изменении правила сначала правится этот документ, затем сервис и его тесты.

## Режимы отправки

| Клавиша | Mode | Смысл |
|---|---|---|
| `Enter` | `Send` | Отправить и запустить как можно скорее (авто-возобновление, если ветка стоит на паузе). |
| `Ctrl+Enter` | `Queue` | Поставить в очередь, не запускать; если ветка не на паузе — сперва поставить на паузу. |
| `Ctrl+Alt+Enter` | `Fork` | Создать новую ветку от текущего листа и запустить её немедленно, не оглядываясь на состояние исходной ветки. |

`ForkSourceId` (устанавливается кнопками "Edit and branch" / "Fork from here" в `MessageFeed`, а не
клавиатурным Fork) — это отдельный, ортогональный признак: если он выставлен, новое сообщение всё
равно уходит в новую ветку (сиблинг текущего листа), но какой mode (`Send`/`Queue`) был нажат —
по-прежнему решает, запускать сразу или ставить в очередь. Другими словами: явный Fork
(`Ctrl+Alt+Enter`) — это единственный способ гарантированно "запустить сейчас", а обычный форк из
сообщения подчиняется тем же правилам, что и Send/Queue.

## Таблица: статус ветки × действие

Статус относится к ветке, на которую фактически ляжет новое сообщение (`runBranchId` —
см. `ChatComposerService.SubmitAsync`, шаг 4): для Fork/ForkSourceId это всегда новая, ещё
не существующая на сервере ветка (трактуется как "нет run").

| Статус ветки | Send (Enter) | Queue (Ctrl+Enter) | Fork (Ctrl+Alt+Enter) |
|---|---|---|---|
| нет run / новая ветка | Enqueue → worker стартует сразу (run создаётся Idle). | Pre-pause (Stop), затем Enqueue → остаётся в очереди до Resume. | Всегда: Enqueue → worker стартует сразу, pre-pause не выполняется никогда. |
| Idle | Enqueue → стартует сразу. | Pre-pause, затем Enqueue → в очереди. | (см. выше — Fork не смотрит на исходный статус) |
| Generating | Enqueue → сообщение встаёт в очередь и стартует автоматически, когда текущая генерация закончится. Текущий ответ **не прерывается**. | Pre-pause (обрывает текущую генерацию!), затем Enqueue → в очереди до Resume. | (см. выше) |
| Completed | Enqueue → стартует сразу (worker трактует Completed как готовность). | Pre-pause, затем Enqueue → в очереди. | (см. выше) |
| Paused | Enqueue, затем авто-Resume → стартует. | Pre-pause не нужен (уже на паузе), Enqueue → остаётся в очереди. | (см. выше) |
| Interrupted | Enqueue, затем авто-Resume → стартует. | Enqueue → остаётся в очереди. | (см. выше) |
| Failed | Enqueue, затем авто-Resume → стартует. | Enqueue → остаётся в очереди. | (см. выше) |

Если авто-Resume (для Send) или pre-pause (для Queue) падает по сети — это best-effort:
сообщение всё равно остаётся в очереди (`Enqueue` уже отработал), просто пользователю может
понадобиться нажать Resume вручную. Никогда не теряем введённое сообщение из-за сетевого сбоя
вспомогательного вызова.

## Edit & Replace

"Edit and replace branch" редактирует прошлое сообщение и **заменяет** ветку целиком (старая
ветка удаляется, новое сообщение цепляется к тому же родителю).

Правило: **замена запрещена, если на этой ветке прямо сейчас идёт генерация** (`Status ==
Generating`). Причина: удаление ветки под работающим ответом обрывает его без возможности
восстановить.

Это проверяется дважды:
1. UI (`MessageFeed`): кнопка "Edit and replace branch" задизейблена, пока `SelectedRun.Status ==
   Generating` — так как `MessageFeed` рендерит только предков текущего `BranchLeafId`, каждое
   показанное сообщение лежит на той же ветке, что и `SelectedRun`, поэтому единой проверки на
   уровне ветки достаточно для любого сообщения в списке.
2. Сервис (`ChatComposerService`): `ComposerSubmitRequest.ReplaceSourceIsGenerating`,
   вычисляемый заново непосредственно перед отправкой — защита от гонки между открытием формы
   редактирования и нажатием Enter/Ctrl+Enter.

Fork и обычный Send/Queue **не** имеют такого ограничения — они не удаляют существующие данные,
поэтому гонка с активной генерацией не приводит к потере ответа.

## Исправленные баги

- `BranchLeafHelpers.RunBranchIdFor` при продолжении **обычной** (не форкнутой) существующей
  ветки возвращал исходный `branchLeafId` вместо `chat.Id` — потому что проверка "дошли до
  корня всего чата" срабатывала для любого листа, форкнутого или нет, а не только для настоящей
  точки форка. Из-за этого `Enqueue`/`Stop` уходили с одним `branchId`, а `Home.razor` читал
  очередь по другому ключу (`GetSelectedRunBranchId()` откатывается на `chat.Id` для не-форкнутых
  веток) — сообщение реально вставало в очередь на сервере, но не отображалось. Исправлено:
  функция теперь ищет ближайшего предка-"не первого сиблинга" (тот же критерий, что и
  `ComputeBranchTreeItems` в Home.razor), и только если такого предка нет — возвращает `chat.Id`.
- Постановка **второго** сообщения в очередь (`Ctrl+Enter`, `Ctrl+Enter`) до того, как отработало
  первое, создавала новую ветку вместо последовательной очереди. Причина: `ParentMessageId` для
  enqueue брался из `branchLeafId` — а он указывает на последнее уже **материализованное**
  сообщение и не продвигается вперёд, пока сообщение только стоит в очереди (диспетчер
  материализует его позже, `ChatRunDispatcher.ProcessAsync`). Оба сообщения уходили с ОДНИМ и тем
  же `ParentMessageId` и после обработки становились сиблингами.
  - Первая попытка исправить это (анкерить новое сообщение на `Id` последнего элемента очереди)
    сама была ошибочной: `Id` элемента очереди — это id его будущего **пользовательского**
    сообщения, а не id ответа ассистента на него (которого ещё не существует). Анкерясь на него,
    следующее сообщение в очереди становилось сиблингом ЕЩЁ НЕ СГЕНЕРИРОВАННОГО ответа — тот же
    баг, только на шаг дальше по цепочке (воспроизведено вживую: msg1/msg2/msg3 подряд в очередь
    → msg2 и msg3 оба показались как отдельные ветки).
  - Итоговое исправление: если у ветки уже есть непустая очередь, `ParentMessageId` не
    указывается вовсе (`null`) — верный id (будущий ответ) на клиенте просто не существует. Вместо
    этого используется уже имеющийся server-side fallback в `ChatRunDispatcher.ProcessAsync`
    (`queued.ParentMessageId ?? chat.Messages[^1].Id`), который на момент реальной обработки этого
    элемента корректно видит только что материализованный ответ на предыдущий.
- Даже с чейнингом выше сообщения всё ещё могли стать сиблингами при **быстром** повторном
  `Ctrl+Enter`: `Home.razor`'s `SubmitComposerAsync` снимал флаг `_isSubmittingMessage` в `finally`
  сразу после ответа сервиса, а `StoreRun(accepted.Snapshot)` (обновление локального кэша ранов,
  от которого зависит чейнинг выше) выполнялся позже. Между этими двумя точками было окно, в
  которое второе быстрое нажатие проходило guard и читало ещё не обновлённый run.
  - Первая попытка исправить это (держать guard, пока весь `OnSubmitAcceptedAsync` не завершится,
    включая `LoadChatsAsync`) сама создавала регрессию: `LoadChatsAsync` — это реальный сетевой
    запрос, и удержание guard на всё это время означало, что третье быстрое нажатие `Ctrl+Enter`
    просто **молча отбрасывалось** (сообщение терялось, а не неправильно анкерилось) —
    воспроизведено вживую.
  - Итоговое исправление: `SubmitComposerAsync` теперь разделяет применение результата на
    `ApplyAcceptedRunState` (синхронно — `StoreRun`, `_selectedChat`, очистка composer; guard
    держится до её завершения) и `FinishAcceptedUiUpdatesAsync` (JS interop, `LoadChatsAsync` —
    выполняется ПОСЛЕ снятия guard, не блокируя следующую отправку).
- Сообщения и ответы при обработке очереди появлялись в UI только после того, как ВСЯ очередь
  отработает — во время обработки был виден только текущий `Generating...`. Это уже не логика
  composer'а, а транспорт run-снапшотов (`ChatRunDispatcher` → SSE → `runEvents.js` →
  `Home.razor.OnRunSnapshot`), но с тем же наблюдаемым эффектом на очередь, поэтому фиксируется
  здесь же. Две независимые причины, обе воспроизведены вживую через реальный сервер:
  - **Сервер** (`ChatRunDispatcher.SubscribeAsync`): канал для SSE-подписчика был
    `Channel.CreateBounded<...>(new BoundedChannelOptions(1) { FullMode = DropOldest })`. Переход
    "Completed" одного элемента очереди публикуется практически без задержки перед "Generating"
    следующего — при вместимости канала 1 более ранний снапшот (`Completed`, именно тот, который
    ждёт клиент) успевал перезаписаться следующим до того, как подписчик его вычитывал.
    Исправлено: вместимость канала увеличена до 64 — этого с большим запасом хватает на серию
    Publish() одного цикла очереди, а `DropOldest` остаётся страховкой на случай, если подписчик
    вообще не читает (отключился).
  - **Клиент** (`runEvents.js`): даже долетевший снапшот мог быть потерян по двум причинам сразу:
    (1) `latest = event.data` — новый снапшот просто перезаписывал ещё не обработанный
    предыдущий ("latest wins", тот же паттерн потери, что и на сервере, только на клиенте);
    (2) диспетчеризация была завязана на `requestAnimationFrame`, который в этом окружении (и,
    как выяснилось ранее в этом же проекте, у части пользователей) ненадёжен и может не
    сработать вовремя или вообще. Исправлено: снапшоты теперь складываются в FIFO-очередь и
    вычитываются ПОЛНОСТЬЮ, без пропусков; диспетч запускается напрямую по событию (обычный
    async-вызов), без `requestAnimationFrame`.
- Голый `Ctrl+Alt+Enter` (без предварительного клика "Fork from here"/"Edit and branch") не
  создавал ветку — сообщение просто добавлялось в текущую ветку как обычное продолжение.
  Причина: shift-логика в Step 3 `ChatComposerService` (перенос на сиблинг листа) срабатывала
  только при `ForkSourceId is not null`; сам `Mode == Fork` никак не проверялся, хотя комментарий
  над кодом ОПИСЫВАЛ это как учитываемый случай. До переноса этой логики из `Home.razor` в
  `ChatComposerService` `ForkFromKeyboard` сама вычисляла точку форка перед вызовом — при
  экстракции сервиса этот расчёт был потерян. Исправлено: условие shift'а теперь также
  срабатывает при `request.Mode == ComposerSubmitMode.Fork`, независимо от `ForkSourceId`.
  Проверено вживую: `Ctrl+Alt+Enter` на обычном сообщении без какого-либо предварительного
  действия создаёт корректный сиблинг (подтверждено и по дереву сообщений через API, и по
  появлению "Choose branch" в UI).

## Индикация статуса ветки/чата/проекта

Единый визуальный язык — маленькая точка (`.status-dot`) перед названием, одна и та же логика
классов ([`RunStatusPresentation`](../src/AI.Client.Web/Runs/RunStatusPresentation.cs)) везде:
project-строка в сайдбаре, chat-строка, branch-tree строка, пункты меню "Choose branch" в
`MessageFeed`. Раньше project/chat/branch-tree строки красились нижней полоской (`::after`), а
пикер веток — точкой; после запроса пользователя на консистентность везде используется точка.

- Пустая (`transparent` заливка, серая обводка) — нет статуса, о котором стоит сообщать.
- Зелёная, мигающая (`run-status-generating`) — идёт генерация.
- Синяя (`run-status-unread`) — есть непрочитанный ответ.
- Красная (`run-status-failed`) — ошибка.
- Серая пунктирная заливка (`run-status-interrupted`) — пауза/прервано.

Точка всегда рисуется (не пропадает при отсутствии статуса) — так пользователь видит одну и ту же
структуру строки везде, а не гадает, есть там место под индикатор или нет.

## Что не покрыто этой таблицей

- Многопользовательские гонки (два клиента одновременно) — вне рассмотрения, у чата есть
  `Revision` для optimistic concurrency на уровне API, но UI-уровень его не проверяет здесь.
- Очередь (`ChatRunSnapshot.Queue`) сама по себе — её reorder/edit/remove API не связаны с
  `ChatComposerService` и в этот документ не входят.
