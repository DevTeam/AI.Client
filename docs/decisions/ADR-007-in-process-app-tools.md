# ADR-007: Инструменты управления приложением во внутрипроцессном MCP-сервере

Статус: Accepted

Дата: 2026-09-15

## Контекст

Модели нужен доступ к данным самого приложения: создать чат из чата, настроить проект под репозиторий, объяснить отказ инструмента, обслужить историю. Данные доступны только через прикладные сервисы Host, которые владеют проверкой ревизий, атомарной записью и рассылкой событий.

Встроенный сервер `AI.Client.Mcp.BuiltIn` — отдельный процесс, работающий по stdio. Он не имеет доступа к этим сервисам. Вариант «дочерний процесс ходит обратно в Host по loopback HTTP» добавляет границу аутентификации ровно там, где [модель безопасности](../06-security.md) уже называет web-to-stdio мост привилегированным риском.

Отдельный вопрос — самоповышение привилегий: инструмент, меняющий directory grants и tool policies, по умолчанию является дырой.

## Решение

### Внутрипроцессный сервер на стандартном протоколе

Прикладные инструменты живут в новом MCP-сервере `AI.Client.Mcp.App`, построенном на библиотеке `ModelContextProtocol`. Он говорит по обычному протоколу — `tools/list`, `tools/call`, JSON-схемы, проверка результата по output schema — и отличается только транспортом: пара in-memory каналов `System.IO.Pipelines` вместо стандартных потоков дочернего процесса.

Самодельная реализация `IToolSession` в обход протокола отвергнута: она дала бы вторую, расходящуюся модель инструмента и обошла бы проверку схем, на которой держатся политики.

`CompositeToolSessionFactory` объединяет stdio-сервер и внутрипроцессный в один набор инструментов. `IToolSessionFactory.OpenAsync` принимает набор идентификаторов серверов, поэтому выключенный сервер не запускается вовсе.

### Пять инструментов по уровню риска

`app_read`, `app_chats`, `app_runs`, `app_projects`, `app_security`. Граница инструмента совпадает с границей того, что пользователь разрешает одной кнопкой `Allow`. Мелкая нарезка по операциям раздула бы список инструментов, а один универсальный сделал бы `Allow` неоправданно широким.

### Отказ от ограничений самоповышения

Агенту доступно всё, что доступно пользователю через UI, включая расширение grants своего проекта и смену политик инструментов `app_*`. Приложение локальное и однопользовательское; агент уже работает с правами учётной записи пользователя и имеет `process_run`, поэтому запрет на уровне этих инструментов создавал бы видимость границы, которой нет.

### Общий сигнал изменения вместо адресного события

Поток `/api/runs/events` получает кадр `data-changed` без полезной нагрузки. Клиент перечитывает то, что показывает. Событие с указанием ресурса и его ревизии потребовало бы поддерживать схему событий в согласии с каждым ресурсом; для локального приложения лишние перечитывания дешевле.

## Последствия

Положительные:

- ревизии, атомарность и события достаются инструментам без дополнительной работы;
- одна реализация сессии обслуживает все серверы, а новый транспорт не размножает код;
- открытый UI видит изменения агента без перезагрузки;
- сторонние MCP-серверы подключаются тем же путём, что и внутрипроцессный.

Отрицательные:

- `app_security` при политике `Allow` может расширить собственные права и включить любой MCP-сервер, то есть выйти за пределы проекта без подтверждения; единственная защита — политика `Ask` по умолчанию;
- рекурсивное порождение чатов ничем не ограничено, кроме лимитов агентского цикла и кнопки остановки;
- журнал идемпотентности живёт в памяти процесса и не переживает перезапуск Host;
- общий сигнал заставляет клиента перечитывать больше, чем изменилось.
